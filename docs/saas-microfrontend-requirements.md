# Dante Cloud SaaS 与微前端改造需求分析

> 状态：需求分析草案，待产品与技术评审
> 编写日期：2026-09-30
> 适用仓库：`rust-saas`
> 范围：定义目标能力、约束和验收口径；本文不代表这些能力已经实现。

## 1. 背景与目标

当前项目已有 Rust/Axum + PostgreSQL 的平台后端、React 管理宿主、租户与多层级组织、应用/菜单/角色授权、OAuth、通知，以及 Vue、jQuery HTML 微应用示例。现有实现适合展示核心流程，但独立业务应用要共享平台身份、租户、组织和权限时，尚缺少完整的服务端授权上下文、可靠的组织切换、生产部署和自动化验证。

本次改造的目标是让 Dante Cloud 成为可承载真实业务的 **SaaS 平台控制层**：统一管理身份、租户、组织、应用、授权、审计和通知；业务应用可以独立开发、部署、发布和回滚，并在自己的后端安全使用平台颁发的应用令牌和权限上下文。

### 1.1 成功判定

1. 两个租户分别拥有多层级组织、独立授权和业务数据；任何普通用户不能读取或修改另一租户的数据。
2. 同一用户切换组织后，宿主和已挂载微应用的 token、菜单、权限及数据范围同步切换，旧上下文不能继续执行受保护请求。
3. 独立部署的业务应用无需复制到主仓库即可发布新版本；平台可配置入口、授权、健康状态与回滚目标。
4. 微应用前端得到展示所需上下文；业务 API 根据服务端验证结果授权，不依赖浏览器传来的菜单或权限数组。
5. 平台和至少一个真实业务应用具备可重复部署、审计、监控、备份和故障回滚能力。

### 1.2 范围边界

- **平台控制层**：用户与会话、租户、组织、部门、成员、角色、应用注册、授权策略、应用令牌、审计和通知。
- **业务应用**：各自的页面、API 和业务数据；遵循平台接入契约。是否使用同一物理数据库由应用团队决定，但必须满足租户隔离要求。
- **可信 HTML 微应用**：通过宿主加载并执行其代码，适用于受平台信任的团队和交付物。
- **不可信或无法改造的外部站点**：使用独立源 iframe 或外链；需要共享上下文时采用受限、版本化的消息协议。
- Athena 演示报表、OAuth 演练站点和现有 Vue/jQuery 示例仅作为改造验证材料，不等同于正式业务应用。

## 2. 现状依据与差距

| 领域 | 当前实现 | 主要差距与影响 |
| --- | --- | --- |
| 租户和组织 | `tenants`、组织树、部门、成员关系及租户/组织授权已存在 | 数据库关系主要依赖单列外键；需要证明父子组织、部门、角色及业务记录不会跨租户串接，并统一所有 API 的数据范围。见 [`0001_init.sql`](../backend/migrations/0001_init.sql)。 |
| 登录上下文 | 登录后选择组织，签发含租户和组织 ID 的 session JWT | 组织/租户有效期在签发上下文时检查；[`CurrentUser`](../backend/src/extractors.rs)主要验证 JWT 和用户状态，需定义成员被移除、组织停用/到期后的即时失效口径。 |
| 会话退出 | `/api/auth/logout` 写审计，前端清除 token | 已签发的 session JWT 没有立即吊销机制；需支持登出、踢出、密码重置后的会话失效。见 [`auth.rs`](../backend/src/routes/auth.rs)。 |
| 权限 | 角色菜单 ∩ 组织菜单 ∩ 租户菜单，30 秒进程内缓存 | 菜单显示、API 操作和业务数据范围尚未形成统一的授权结果；多实例缓存失效也需设计。见 [`state.rs`](../backend/src/state.rs)。 |
| 应用令牌 | 微应用容器尝试向 `/api/oauth/session-token` 申请应用 access token | 签发端当前按 `appCode` 找客户端，没有再次校验用户在当前租户/组织是否获该应用授权；快速接入也不会自动建 OAuth 客户端。见 [`oauth2.rs`](../backend/src/routes/oauth2.rs)。 |
| 对外数据 | `/api/external/menus`、`/roles` 可用 access token 调用 | 返回的是关联应用的启用菜单和获授权组织角色概览，不能作为当前用户的有效权限结果。见 [`external.rs`](../backend/src/routes/external.rs)。 |
| 微应用宿主 | HTML 入口、沙箱、ESM 入口、生命周期和基础 props 已有 | props 缺租户、组织、有效权限和角色；组织切换后的 token/上下文刷新不完整；沙箱用于资源回收，不是安全边界。见 [`MicroAppContainer.tsx`](../frontend/src/components/micro/MicroAppContainer.tsx)和 [`sandbox.ts`](../frontend/src/components/micro/sandbox.ts)。 |
| 通知 | 后端通知表和 `pg_notify`，独立 Socket.IO 服务；`onNotify` 可显示 Toast | `onNotify` 只是界面提示，不会入库；通知服务配置依赖原开发环境，当前 Compose 未编排它。见 [`notification-ws`](../mini-services/notification-ws/index.ts)。 |
| 发布 | Compose 管理数据库、后端与 Caddy Web；前端静态子应用可随主站发布 | 独立应用的注册、版本、健康、发布和回滚尚无统一流程；示例数据库入口仍含开发代理或 Vite 源码路径。见 [`docker-compose.yml`](../docker-compose.yml)与 [`0011_micro_frontend.sql`](../backend/migrations/0011_micro_frontend.sql)。 |
| 验证 | 有少量 shell 运行时脚本和示例 smoke test | 缺跨租户越权、上下文切换、令牌撤销、微应用契约和完整发布链路的统一验收集。 |

## 3. 用户与职责

| 角色 | 主要职责 | 可见边界 |
| --- | --- | --- |
| 平台运维管理员 | 配置平台级应用、租户、接入策略、密钥和部署状态 | 平台范围；跨租户操作需单独审计 |
| 租户管理员 | 管理本租户组织、成员和可用应用的授权 | 本租户；不得修改其他租户或全局应用定义 |
| 组织管理员 | 管理授权范围内的组织、成员、角色和菜单 | 当前组织及经明确授权的子组织范围 |
| 普通用户 | 选择组织、访问获授权应用并处理业务 | 当前会话组织和被授予的数据范围 |
| 微应用开发者 | 实现接入契约、业务 API、发布与健康检查 | 所属应用的注册与发布权限 |
| 审计/安全人员 | 查询登录、授权、发布和跨租户操作记录 | 由平台策略授予的审计范围 |

平台管理员与租户管理员的能力必须在服务端区分，不能仅靠前端隐藏入口。

## 4. 业务对象和规则

### 4.1 核心对象

`User` 是平台身份；`Membership` 将用户关联至组织，组织归属租户；`Role` 在组织范围内定义；`Application` 是全局应用注册；应用及菜单经过租户、组织和角色授权后对用户生效。业务应用的记录必须携带可验证的租户归属，组织范围数据还需携带组织归属。

### 4.2 拟采用的授权计算

在选定上下文 `(userId, tenantId, organizationId, appCode)` 下：

1. 验证用户、租户、组织、成员关系和应用状态。
2. 验证租户与组织获得应用授权。
3. 计算当前组织上下文中的有效角色，再与租户菜单、组织菜单及应用菜单求交，形成可见菜单和操作权限码。
4. 根据角色的数据范围策略，得到 `SELF | ORG | ORG_SUBTREE | TENANT` 等数据范围。默认拒绝，具体枚举与继承规则需在评审中最终确认。
5. 返回带版本号与过期时间的应用上下文；权限变更、成员移除、组织停用后使旧版本失效。

菜单/权限码用于界面和操作授权；业务记录的数据范围还需要在服务端查询条件或数据库策略中落实。超级管理员的跨租户权限必须作为平台级能力显式审计。

## 5. 功能需求

优先级：**P0** 为上线前必须完成，**P1** 为首个真实业务应用接入前完成，**P2** 为规模化运营能力。每条需求的验收口径是实施与测试的依据。

### 5.1 租户、组织与成员

| ID | 优先级 | 需求 | 验收口径 |
| --- | --- | --- | --- |
| TEN-01 | P0 | 每次受保护请求都基于有效租户、组织和成员关系建立上下文；禁用或到期状态按统一策略生效。 | 移除成员、停用组织或租户后，旧会话在约定时限内不能继续读取或写入受保护资源。 |
| TEN-02 | P0 | 普通租户请求的租户范围由服务端上下文确定，不能由请求参数覆盖；列表、详情、修改、删除、导出一致。 | 使用另一租户 ID 发起各类请求均被拒绝或返回不可见。 |
| TEN-03 | P0 | 组织父子关系、部门父子关系、成员部门及角色组织归属必须保持同租户/同组织约束。 | API 与数据库约束都拒绝跨租户、跨组织错误关联；已有数据有审计与修复迁移。 |
| TEN-04 | P1 | 定义多组织成员、祖先角色继承、子组织访问与数据范围规则，并在后台展示生效范围。 | 同一用户处于总部、分公司上下文时，权限和数据结果与规则矩阵一致。 |
| TEN-05 | P1 | 租户与组织停用、到期、删除采用明确的数据保留和恢复策略。 | 管理员能预览影响范围；审计和业务数据按保留政策处理，不因误操作无提示丢失。 |

### 5.2 身份、会话和应用令牌

| ID | 优先级 | 需求 | 验收口径 |
| --- | --- | --- | --- |
| IAM-01 | P0 | 区分平台 session、登录票据、面向单个应用的 access token；每类令牌只能用于预期接口。 | 错误类型或错误应用受众的令牌均被拒绝。 |
| IAM-02 | P0 | 应用令牌签发前验证当前用户的成员身份及租户/组织/应用授权，并绑定 `sub`、`tenant`、`org`、`aud/appCode`、到期时间与唯一标识。 | 未授权应用、已停用应用或被移除的成员无法取得该应用令牌。 |
| IAM-03 | P0 | 支持登出、管理员踢出、密码重置、权限撤销后的会话/应用令牌失效。 | 失效时限可配置且可测试；被撤销令牌不能通过内省和业务 API。 |
| IAM-04 | P1 | 宿主负责应用令牌续期；微应用只在内存中使用令牌，并通过上下文更新收到新令牌。 | 长时间停留、网络重连和组织切换后不会使用过期或旧组织令牌。 |
| IAM-05 | P1 | 独立业务后端通过受保护的内省接口或公钥机制验证令牌，不复制平台签名密钥至应用。 | 应用服务端能验证有效期、受众、撤销状态和上下文；客户端密钥不出现在浏览器包中。 |
| IAM-06 | P1 | 生产环境采用明确的浏览器会话存储与 XSS/CSRF 防护策略，并禁止演示默认密钥和密码。 | 安全评审通过，默认凭据不进入生产配置，登录与续期流程可用。 |

### 5.3 授权、菜单与数据范围

| ID | 优先级 | 需求 | 验收口径 |
| --- | --- | --- | --- |
| AUTH-01 | P0 | 提供单一授权计算服务，输出当前应用的可见菜单、角色、权限码和数据范围；前端与业务后端使用同一口径。 | 同一上下文在宿主、微应用和业务 API 中得到一致结果。 |
| AUTH-02 | P0 | 每个受保护业务操作在服务端校验操作权限和租户/组织数据范围，默认拒绝。 | 直接调用隐藏按钮对应 API 或篡改资源 ID 仍被拒绝。 |
| AUTH-03 | P0 | `/api/external/menus`、`/roles` 等对外接口区分管理视图与当前用户视图；用户视图不得泄露其他组织角色和应用全部菜单。 | 普通应用令牌只能读取其当前用户、租户、组织和应用范围内的数据。 |
| AUTH-04 | P1 | 授权变更具备版本或事件驱动失效机制，跨后端实例保持一致。 | 变更后在约定时限内宿主菜单、上下文接口及业务 API 同步更新。 |
| AUTH-05 | P1 | 授权编辑具备影响预览、操作审计和必要的撤销/恢复路径。 | 管理员能定位谁在何时改变了哪个租户/组织/角色的授权。 |

### 5.4 应用注册、微前端和独立发布

| ID | 优先级 | 需求 | 验收口径 |
| --- | --- | --- | --- |
| APP-01 | P1 | 应用注册保存编码、类型、入口、资源基址、环境、版本、状态、信任级别、健康地址和令牌受众；租户授权与部署版本分离。 | 同一应用可独立升级/回滚；授权记录不因换版本丢失。 |
| APP-02 | P1 | 可信 HTML 微应用支持独立域名发布，并通过主站同源网关路径接入；资源地址与路由基址可配置。 | 发布微应用新版本无需重新构建宿主；入口、JS、CSS 请求指向正确版本。 |
| APP-03 | P1 | 提供版本化生命周期契约 `mount/update/unmount` 和轻量接入 SDK；`update` 接收完整上下文与变更版本。 | Vue、jQuery 示例通过契约测试；反复切换应用后无持续运行的计时器、监听器或样式污染。 |
| APP-04 | P0 | 宿主在组织、应用或用户上下文变化时停止旧请求、撤销旧 props、取得新 token/权限后再更新或重挂微应用。 | 快速连续切换组织时不会显示或使用旧组织的 token、菜单和业务数据。 |
| APP-05 | P1 | 加载器提供超时、错误提示、重试、版本一致性与资源缺失识别；子应用文件缺失返回 404。 | 无法访问入口或 JS 时可定位错误，不把主站 `index.html` 当作脚本执行。 |
| APP-06 | P1 | 不可信或难以适配生命周期的应用走独立源 iframe/外链；如需上下文通信，使用限定 `origin`、版本和消息类型的协议。 | 未列入信任清单的脚本不能在宿主页面上下文执行；消息来源和目标均被校验。 |
| APP-07 | P2 | 接入流程提供预检：入口可访问、资源 MIME、生命周期、健康、授权链和令牌客户端状态。 | 管理员在启用前可看到可操作的检查结果。 |

### 5.5 应用上下文与对外接口

| ID | 优先级 | 需求 | 验收口径 |
| --- | --- | --- | --- |
| CTX-01 | P0 | 新增按应用令牌返回当前用户、租户、组织、菜单、角色、权限和数据范围的服务端上下文接口。 | 未授权应用或错误受众返回 403；返回值不含其他租户或组织数据。 |
| CTX-02 | P1 | 上下文响应含 `version`、`expiresAt`，字段语义和兼容策略有文档及契约测试。 | 宿主与独立应用能识别过期或不同版本契约。 |
| CTX-03 | P1 | 业务 API 接入组件统一完成令牌校验、上下文获取、资源归属检查和拒绝响应。 | 至少一个真实业务应用复用该组件完成全部受保护接口。 |
| CTX-04 | P1 | 对外接口将“当前用户有效菜单/权限”与“平台管理配置”分开命名和鉴权。 | 普通应用令牌无法访问管理配置接口。 |

建议的上下文响应形状如下；具体字段与权限继承规则在设计评审后冻结：

```json
{
  "contractVersion": "1.0",
  "contextVersion": 42,
  "expiresAt": "2026-09-30T10:00:00Z",
  "appCode": "example",
  "user": { "id": "...", "username": "...", "displayName": "..." },
  "tenant": { "id": "...", "code": "...", "name": "..." },
  "organization": { "id": "...", "name": "...", "path": "..." },
  "roles": [],
  "permissions": ["example:order:read"],
  "dataScope": { "type": "ORG_SUBTREE", "organizationIds": [] },
  "menus": []
}
```

### 5.6 通知、审计和运营

| ID | 优先级 | 需求 | 验收口径 |
| --- | --- | --- | --- |
| MSG-01 | P1 | 将 `onNotify` 明确定义为瞬时界面 Toast；持久通知使用单独的受权发布接口。 | 调用 Toast 不生成站内消息；发布通知可查询、标记已读并审计。 |
| MSG-02 | P1 | 业务应用发布通知时验证应用身份、租户范围、目标用户/组织与权限，支持去重键和失败重试。 | 无法向其他租户用户发送；重复请求不会造成不可控的重复消息。 |
| MSG-03 | P1 | 实时推送服务具备环境配置、健康检查、认证、重连和可观测性，并纳入部署编排。 | 断线后站内记录仍可查询，恢复连接后未读状态正确。 |
| AUD-01 | P0 | 登录、上下文切换、授权、令牌签发/吊销、应用发布和跨租户管理有结构化审计。 | 可按主体、租户、组织、应用、请求 ID 和时间追踪关键操作。 |

## 6. 非功能需求

以下量化值是**建议验收目标**，评审后再固化为 SLA/SLO，不应视为当前项目性能承诺。

| ID | 级别 | 需求与建议目标 |
| --- | --- | --- |
| NFR-01 | P0 | 安全：全站 HTTPS；生产密钥由密钥服务或受控环境变量提供；禁止默认账户密码；限制 CORS、CSP 和第三方脚本来源；日志不得包含明文 token、密码或客户端密钥。 |
| NFR-02 | P0 | 隔离：每个受保护 API 至少覆盖“跨租户 ID、跨组织 ID、越权角色、已撤销授权”四类负向测试；数据库迁移前扫描存量异常关系。 |
| NFR-03 | P1 | 权限时效：成员移除、组织停用、角色撤销后，旧授权在建议的 60 秒以内失效；更严格的业务可按需缩短。 |
| NFR-04 | P1 | 可用性：网关、平台 API 和通知服务均提供健康检查；应用加载失败可回退至错误页并手动重试，不影响宿主其它应用。 |
| NFR-05 | P1 | 性能：在约定的测试数据规模下，应用上下文接口的建议 P95 响应时间不超过 300 ms；菜单树和组织树需分页或按需加载的规模阈值另行确认。 |
| NFR-06 | P1 | 发布：静态入口使用短缓存或版本化地址，带哈希的资源可长期缓存；部署可回滚至上一版本，缺失资源不走 SPA fallback。 |
| NFR-07 | P1 | 数据保护：数据库自动备份、定期恢复演练；租户停用、删除和数据导出按明确保留期执行。RPO/RTO 与保留期由业务确定。 |
| NFR-08 | P1 | 可观测性：统一请求 ID、结构化日志、错误率/延迟/令牌失败/权限拒绝/微应用加载失败指标；告警能定位到租户和应用但不泄露敏感信息。 |
| NFR-09 | P2 | 兼容性：接入契约提供版本与废弃周期；Vue、React、jQuery HTML 子应用可按同一协议接入。 |

## 7. 关键业务流程

### 7.1 用户进入独立业务应用

1. 用户登录平台并选择组织；平台确认成员、租户和组织均有效。
2. 宿主获取当前组织可用应用、当前应用菜单和有效权限；用户选择应用。
3. 平台确认该应用在租户、组织范围内获授权，为用户签发受众限定的短期应用 token。
4. 宿主加载该应用的可信 HTML 入口，调用 `mount(container, props)`；props 含展示上下文与 token。
5. 应用前端调用自身业务 API。业务后端验证 token 和应用上下文，再校验操作权限及记录的租户/组织归属。
6. 角色、组织或授权变化时，平台更新上下文版本，宿主和业务后端均拒绝旧上下文并刷新。

### 7.2 切换组织

宿主暂停旧上下文请求，向平台换取新组织 session，清理旧应用令牌和缓存，重新计算可用应用、菜单、权限与数据范围。若当前应用在新组织不可用，则离开该应用；若仍可用，则签发新应用 token 并以完整新上下文调用 `update` 或重新挂载。旧组织请求即使延迟返回，也不得覆盖新组织页面。

### 7.3 发布与回滚微应用

应用团队构建、验证并部署带版本的资源；平台执行入口可用性、MIME、生命周期及健康检查。管理员或自动发布流程将应用注册指向新版本。出现加载/运行错误时切回上一版本；租户和角色授权不随部署版本变化。具体审批与自动化策略由运维流程确定。

## 8. 数据和接口设计约束

1. 平台身份可以跨租户；业务记录的租户归属必须唯一且不可由普通请求任意改写。各业务应用可有独立数据库，但仍遵守同一上下文和权限校验协议。
2. 组织树、部门树、角色和成员关系需在应用层与数据库层双重约束。已执行的 SQLx 迁移不直接修改；新增迁移负责结构变更与存量修复。
3. 应用定义由平台维护；租户授权、组织授权、角色菜单、部署版本和租户个性化配置应分开存储，避免一次发布重写授权。
4. 对外令牌校验必须覆盖签名或内省结果、过期、撤销、受众、用户状态、租户和组织状态、应用授权及上下文版本。浏览器传来的 ID、菜单和权限不得覆盖校验结果。
5. API 错误约定区分未登录、无权、资源不可见、冲突与暂时不可用；跨租户资源建议统一返回不可见结果以减少枚举信息，具体口径在 API 设计时确定。
6. 平台应为微应用提供可用的权限上下文接口，而不是让其调用管理接口推导权限；当前 `/api/external/menus`、`/roles` 语义需要调整或更名。

## 9. 迁移与交付阶段

| 阶段 | 建议交付 | 退出条件 |
| --- | --- | --- |
| M0：规则冻结与基线 | 确定组织继承、数据范围、平台管理员、可信应用边界；补存量数据审计和跨租户测试矩阵 | 关键规则有评审结论；现有数据异常有处理方案 |
| M1：租户与身份安全 | 请求上下文重新校验、应用签发授权、会话失效、数据库约束和 API 隔离修复 | 跨租户与撤销测试通过；默认密钥/账号不进入生产 |
| M2：统一授权上下文 | 授权计算服务、应用上下文接口、受众限定 token、权限版本及业务后端接入组件 | 宿主、上下文接口、业务 API 权限一致；组织切换无旧数据回流 |
| M3：微应用标准化 | 版本化 SDK、注册/预检、同源代理、错误与回滚；Vue 示例接入完整上下文 | Vue 应用独立发布且无需重建宿主；契约测试通过 |
| M4：业务试点与通知 | 一个真实业务应用、持久通知发布接口、通知服务生产编排；jQuery 示例按契约或 iframe 接入 | 真正业务数据的租户/组织隔离通过端到端验收 |
| M5：运营与规模化 | CI/CD、备份恢复、监控告警、发布审计、接入手册 | 可重复部署、回滚和故障演练通过 |

先完成 M1/M2 再扩大微应用数量。现有“快速接入”可继续服务演示和简单内部应用，生产接入须通过上下文、后端鉴权和发布预检。

## 10. 端到端验收场景

| 场景 | 预期结果 | 关联需求 |
| --- | --- | --- |
| 租户 A 用户请求租户 B 的用户、组织、角色、审计或业务记录 | 全部拒绝或不可见，且不能通过导出绕过 | TEN-02、AUTH-02、NFR-02 |
| 用户在组织 X 获应用授权，在组织 Y 无授权，切换到 Y | 应用从可用列表消失，无法签发 Y 的应用令牌，旧 token 不能继续执行 Y 的业务请求 | TEN-01、IAM-02、APP-04 |
| 用户角色移除或菜单授权撤销 | 页面、上下文接口与业务 API 在约定时限内同步失去权限 | IAM-03、AUTH-04 |
| 微应用尝试以 A 应用 token 访问 B 应用 API | 服务端按受众拒绝 | IAM-01、IAM-05 |
| 微应用只隐藏按钮，但直接调用对应写 API | 服务端按权限和数据范围拒绝 | AUTH-02 |
| 独立微应用版本发布、资源缺失和回滚 | 新版本可加载；缺失 JS 为 404；回滚后旧版本恢复，不更改授权 | APP-02、APP-05、NFR-06 |
| 微应用调用 Toast 与持久通知发布接口 | Toast 只显示界面提示；持久通知入库、推送、可追踪且不能跨租户发送 | MSG-01、MSG-02、MSG-03 |
| 微应用多次挂载、切换主题/路由、卸载 | 状态更新正确，定时器、监听器和样式无持续泄漏 | APP-03 |

## 11. 待评审决策

| 决策 | 推荐起点 | 需要确认的问题 |
| --- | --- | --- |
| 组织角色继承 | 祖先组织角色可作用于子组织，但数据范围单独计算 | 子组织是否能拒绝继承？成员未直接加入子组织时能否访问？ |
| 数据范围 | `SELF/ORG/ORG_SUBTREE/TENANT`，默认最小范围 | 是否需要项目级或自定义资源范围？ |
| 租户数据存储 | 平台共享 PostgreSQL，业务应用按 `tenant_id` 隔离；重要业务可独立库 | 是否存在监管或合同要求的租户独立库？ |
| 令牌验证 | 短期应用 token + 服务端内省/公钥验证，明确撤销时效 | 应用后端是否能访问平台内省接口？目标失效时限是多少？ |
| 微应用信任级别 | 可信团队使用 HTML 入口；外部未知代码使用 iframe | 哪些团队可直接在宿主页面执行脚本？ |
| 发布治理 | 先支持版本登记、健康预检和人工回滚 | 上线是否需要审批、灰度和按租户分批发布？ |
| 可用性和保留期 | 先按 NFR 建议值验证 | 正式 SLA、RPO/RTO、审计及业务数据保留期是多少？ |

## 12. 非目标与文档关系

本次首阶段不要求将 Rust 后端拆成多个服务、不要求所有租户采用独立数据库、不要求重写 Vue/jQuery 示例为同一前端框架，也不把 HTML 沙箱当作隔离恶意代码的机制。是否增加计费、套餐、支付、工单或多区域部署应另立需求。

本文是需求基线；具体字段、SQL、API 请求/响应、部署命令及任务拆分在方案评审后分别写入设计文档和实施计划。现有说明可参照 [项目文档](../README.md)、[API 契约](./api-contract.md)、[数据库设计](./db-schema.md)及[微前端接入指南](./microfrontend-integration.md)，但后续实现以实际代码和新签署的接口契约为准。
