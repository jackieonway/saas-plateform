# 授权与组织作用域规则矩阵（Phase 1 草案）

> 状态：Q1/Q2 已于 2026-09-30 获用户确认；Q3 及具体业务资源归属仍待确认。本文记录当前代码行为、确认的目标规则和后续阶段依赖。
> 基线：`docs/saas-microfrontend-requirements.md`、`backend/src/state.rs`、`backend/src/routes/auth.rs`、`backend/src/extractors.rs` 和 `backend/migrations/0001_init.sql`。

## 1. 术语与边界

| 概念 | 含义 |
| --- | --- |
| 平台身份 | `users` 中的全局用户；可在不同租户的组织各有一条 `memberships`。 |
| 会话上下文 | 一个 session JWT 中绑定的 `tenant` 与 `org`；一次请求只能使用这一个组织上下文。 |
| 直接成员 | 用户在目标组织拥有 `memberships` 记录。 |
| 祖先角色 | `roles.organization_id` 位于当前组织的祖先链，且用户拥有该角色。当前 `state.permissions_of` 使用此口径。 |
| 应用/菜单授权 | 应用和菜单需同时在租户和当前组织获授权；角色菜单还需包含目标菜单。 |
| 数据范围 | 业务 API 对记录集合的服务端过滤，不等同于菜单可见性。 |

## 2. 当前代码事实

1. 登录和 `POST /api/auth/context` 会验证所选组织的直接成员身份；后者还检查租户/组织到期时间。`CurrentUser` 对后续请求验证 JWT 类型/签名和用户启用状态，没有逐请求查询成员资格、组织/租户状态或到期时间。
2. `state.permissions_of(user_id, org_id)` 从当前组织向上找角色所属组织，再与当前组织菜单、租户菜单求交，缓存 30 秒；`user_roles.organization_id` 在此查询中未参与限定。
3. `/api/auth/menus` 的普通用户分支按角色、组织、租户三层菜单求交；`/api/auth/profile` 的应用列表按租户应用与组织应用交集返回。超级管理员权限检查有直通分支。
4. `organizations.parent_id`、`departments.parent_id`、`memberships.department_id`、`roles.tenant_id` 与 `roles.organization_id` 当前由单列外键分别约束；没有数据库复合约束保证相关记录同租户或同组织。部分 API 有应用层校验，但数据库直写或漏校验路径仍需审计。
5. 租户唯一根组织由迁移 `0009_task18_batch.sql` 的部分唯一索引约束；组织环路和跨租户父节点仍需额外检测。

## 3. 已确认的目标规则

### 3.1 组织进入与角色继承

- 用户只能选择自己**直接加入**且有效的组织。仅属于祖先组织，不自动获得进入子组织的资格。
- 进入目标组织后，可继承该组织祖先链上明确授予用户的角色；继承的角色菜单仍必须通过目标组织和租户的授权交集。
- 角色继承只决定菜单与操作权限。业务数据范围由独立的数据授权决定，不从角色推导。
- 平台级跨租户管理是单独的显式能力；普通租户管理员即使持有同名权限码，也不能执行平台范围操作。

### 3.2 数据范围

| 范围 | 推荐含义 | 查询边界 |
| --- | --- | --- |
| `SELF` | 用户本人创建、负责或明确关联的记录 | 必须由业务表中可验证的用户归属字段限定 |
| `ORG` | 当前会话组织的记录 | `tenant_id` 和 `organization_id` 同时匹配 |
| `ORG_SUBTREE` | 当前组织与其有效子孙组织的记录 | 限当前租户，并使用无环组织树计算后代 |
| `TENANT` | 当前租户的记录 | `tenant_id` 匹配当前会话租户 |

缺省无权限。业务 API 的操作权限与独立数据授权同时满足后才允许读写；客户端提交的租户、组织、资源 ID 只能缩小结果，不能扩大已认证范围。四级范围及默认拒绝已确认。首版数据策略显式绑定当前组织直接成员、应用、资源和操作；`SELF` 在各业务资源上的归属字段由接入时声明并由后端校验。

## 4. 行为矩阵

下表的“目标结果”按第 3 节已确认规则编写，用作测试设计；并非全部已实现。

| 场景 | 目标组织直接成员 | 有效角色来源 | 目标结果 | 当前代码/风险 |
| --- | --- | --- | --- | --- |
| 用户直接加入组织 A，角色属于 A，租户/组织/角色都获应用与菜单授权 | 是 | A | 允许菜单和操作；数据另按独立授权过滤 | 基本授权链已有。 |
| 用户直接加入 A 的子组织 A1，角色属于祖先 A | 是 | A | 角色可继承；仍需 A1 与租户菜单授权 | 当前角色祖先链逻辑基本支持。 |
| 用户只加入 A，尝试进入子组织 A1 | 否 | A | 拒绝签发 A1 会话 | `POST /api/auth/context` 会拒绝；旧 token 的持续有效性需后续补齐。 |
| 用户加入 A1，但 A1 未获目标应用或菜单授权 | 是 | A 或 A1 | 拒绝该应用/菜单 | 当前 profile/menus 有交集过滤；应用 token 签发尚缺同样校验。 |
| 用户同时加入租户 A 的 A1 和租户 B 的 B1，当前会话为 A1 | 是 | A 链 | 不得访问 B 数据或角色 | 平台管理 API、对外 API、业务 API 和数据库关系都需负向验证。 |
| 用户从 A1 成员列表移除，但持有旧 A1 session | 否 | 任意 | 在已批准的失效时限内拒绝 | 当前 `CurrentUser` 不逐请求查成员，存在旧会话窗口。 |
| A1 或其租户被停用、到期，用户持有旧 session | 原有 | 任意 | 在已批准的失效时限内拒绝 | 到期主要在签发时检查；逐请求规则待改造。 |
| 租户管理员尝试操作另一租户对象 | 取决于当前租户 | 本租户 | 拒绝/不可见，并记录安全审计 | 多个路由已有作用域检查，但需全量矩阵。 |
| 平台管理员执行经授权的跨租户管理 | 平台上下文 | 平台角色 | 允许并记录目标租户、资源、操作者 | 当前有 `is_platform_context` 与超管直通；审计字段需统一。 |
| 独立数据授权赋予 `ORG_SUBTREE`，操作目标属于无关组织或另一租户 | 是 | 当前组织链 | 拒绝 | 数据范围尚无统一计算与业务查询落实。 |

## 5. 需要确认的业务决策

| ID | 选项 | 推荐值 | 影响 |
| --- | --- | --- | --- |
| Q1a | 仅直接成员可进入目标组织；或祖先成员可直接进入子组织 | 仅直接成员 | 决定会话签发、成员关系、组织树访问及测试夹具。 |
| Q1b | 祖先角色继承；或只使用目标组织角色 | 祖先角色继承 | 决定角色菜单与权限计算，现有代码倾向继承。 |
| Q1c | 子组织能否拒绝祖先角色继承 | 首版不提供拒绝覆盖 | 若允许拒绝，需要显式 deny 规则及冲突优先级。 |
| Q2a | 数据范围采用四级枚举；或项目级/自定义资源策略 | 首版四级，后续扩展 | 决定数据模型、业务 API 适配器和用户界面。 |
| Q2b | 数据范围是否从角色推导 | 不从角色推导，独立授予数据策略 | 角色变更只影响菜单与操作权限；数据授权单独审计和撤销。 |
| Q2c | `SELF` 归属字段由平台统一，还是由业务应用声明 | 应用在接入契约中声明并由后端校验 | 不同业务实体可能没有统一的 `created_by` 语义。 |
| Q3 | 停用/到期/成员移除的目标失效时限 | 需求草案建议不超过 60 秒 | 决定会话版本、缓存和应用令牌 TTL。 |

用户已确认 Q1a～Q1c 的推荐组织进入与角色继承规则、Q2a 的四级范围和默认拒绝，并明确要求角色与数据权限分离；首版数据授权按直接成员、应用、资源和操作显式绑定。Q2c 的 `SELF` 归属字段在每个业务资源接入时声明并校验，缺少可靠字段则拒绝该范围的数据访问。

## 6. Phase 2 数据库约束前置结论

- 与产品规则无关的**同租户/同组织一致性**可以先准备：组织父节点与子节点同租户、部门父子同组织、成员所选部门属于其组织、角色的 `tenant_id` 等于其组织的 `tenant_id`。
- 组织树无环是结构不变量；无论是否允许祖先角色继承，都需要检测并防止环路。
- `user_roles.organization_id` 的业务语义必须确认。当前写路径通常填角色所属组织，但权限查询不使用该列；迁移前先审计存量，不直接更改其含义。
- 应先在实际数据库运行只读审计 SQL，再选择拒绝迁移或经审批修复异常；不得静默删除或重写用户授权。
