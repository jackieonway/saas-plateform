# 0013 组织关系约束迁移说明（Phase 2）

> 状态：迁移已在隔离 PostgreSQL 17.6 验证；生产环境尚未执行。
> 文件：`backend/migrations/0013_tenant_relationship_integrity.sql`。

## 1. 目标和边界

迁移增加数据库级的**结构一致性**，不改变角色继承、成员能否进入子组织或业务数据范围等待评审规则。已应用的 `0001`～`0012` 迁移保持原样。迁移不自动删除、移动或重写任何用户、成员或授权记录。

| 关系 | 新数据库约束 |
| --- | --- |
| 组织子节点 → 父节点 | `(parent_id, tenant_id)` 必须指向同租户组织。 |
| 部门子节点 → 父节点 | `(parent_id, organization_id)` 必须指向同组织部门。 |
| 成员 → 部门 | `(department_id, organization_id)` 必须指向成员所在组织的部门；空部门允许。 |
| 角色 → 组织 | `(organization_id, tenant_id)` 必须与角色的租户一致。 |
| 组织和部门树 | 插入/调整父节点时拒绝环路；同租户/组织层级变更使用事务级 advisory lock 串行化。 |

`user_roles.organization_id` 的最终业务含义仍待规则确认；本迁移只审计它，不强加新的复合外键。应用、菜单、角色授权链的动态包含关系由 Phase 3/6/7 继续处理。

## 2. 存量库迁移步骤

1. 备份目标数据库，并在隔离副本上先运行 [`tenant-relationship-audit.sql`](./sql/tenant-relationship-audit.sql)。保存异常行及数量。
   项目根目录提供 [`.env.test.example`](../.env.test.example)；将其复制为 Git 忽略的 `.env.test` 并填写 `TEST_DATABASE_URL`。不得指向生产数据库。
2. 对跨租户父节点、跨组织部门、成员部门不匹配、角色租户不匹配或树环路逐条确认正确归属。可能的处理是更正归属、重建合法关系或暂缓迁移；不得根据 ID 自动猜测并改写授权。
3. 在隔离副本执行 SQLx 迁移 `0013`。迁移开头的预检会在发现上述结构异常时抛错并中止，防止一部分约束生效、一部分失败。
4. 执行 [`tenant-relationship-constraints.sql`](../tests/tenant-relationship-constraints.sql)，确认正常关系仍能插入，六类非法关系被拒绝。
5. 将审计、异常处理、迁移和测试结果作为发布记录。生产执行按已批准的维护窗口、备份与回滚方案进行。

若原库已执行到 `0012`，无需改旧迁移；后端启动时 SQLx 会按顺序执行新迁移。由于新增约束可能需要扫描大表，生产环境需先在数据量相近的副本评估锁等待和迁移时长。

## 3. 回滚与兼容

- 迁移自身不转换业务数据；PostgreSQL/SQLx 在迁移失败时回滚该迁移事务。存量异常应在单独、可审计的修复事务中处理。
- 若上线后需要撤销约束，应创建新的后续迁移，明确删除哪些新外键、触发器、函数和索引；不要改写 `0013` 的内容或 SQLx 校验和。
- 现有 API 的合法插入路径可继续工作。数据库直写和漏掉归属校验的路径可能从“写入成功”变为外键错误，需要在 Phase 3 中统一映射为清晰的业务错误。
- `0009` 已有“每租户一个根组织”部分唯一索引；`0013` 的父节点约束与其互补。

## 4. 已完成的离线验证

- 使用 `pglast` 解析迁移与测试脚本，语法通过。
- 使用隔离的 PGlite 顺序执行 `0001`～`0013` 全部迁移，执行成功；在 `0001` → `0013` → 约束测试中，合法数据通过，跨租户组织、跨组织部门、成员部门不匹配、角色租户不匹配、组织环路、部门环路均被拒绝。
- 在模拟已有库中，合法已有数据可迁移；预先插入跨租户组织父节点时，`0013` 的预检按预期拒绝迁移。
- 在模拟异常旧库中，只读审计 SQL 检出跨租户组织父节点和组织环路，证明异常报告可用于预检失败定位。
