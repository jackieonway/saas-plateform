# 为普通工单用户配置功能权限与数据范围

本指南使用已有“授权管理”“角色管理”“用户管理”和 `/system/data-grants` 页面，为指定普通用户在指定组织内开通或撤销工单能力。管理员无需直接修改平台数据库。页面与接口的配置、严格边界和完整示例见[受控数据 grant 管理](data-grant-management.md)，实际验收见 [Phase 15](validation/phase-15.md)。

示例只讨论工单的 `ticket` 资源，不混用门店资源。租户、组织、应用、用户和成员都从当前获授权的真实选项中选择；本文没有可直接套用的生产 UUID，也不要求给所有动作授予 TENANT。

## 先区分三种授权

| 授权 | 决定什么 | 怎样配置 |
| --- | --- | --- |
| 应用、菜单与按钮 | 用户是否能进入工单、查看详情、创建、更新、删除或导出 | 租户应用/菜单 → 组织应用/菜单 → 角色菜单 → 用户角色 |
| 业务 data grant | 某个直接成员对 `ticket:read` 等具体操作能访问哪些业务记录 | “数据授权”页面逐 resource/action 选择已登记 scope |
| grant 管理权限 | 谁能查看或修改上述 data grant | 独立 read/write 权限、管理页面 MENU、当前上下文及服务端策略 |

角色可以按既有组织祖先链提供功能菜单权限，但仍受当前租户和组织授权上限约束。data grant 绑定用户在**当前组织的有效直接成员**，不随祖先角色继承。一个人在两个组织使用同一角色，也需要分别核对两个直接成员的数据授权。仅有角色、菜单或按钮，缺少对应 grant 时业务操作仍默认拒绝。

执行功能授权的人需要原管理页面的权限。grant 只读管理者需要 `system:data-grant:read`、已获授权的 `/system/data-grants` MENU 及可读管理范围；修改者还必须处于实际平台租户根组织上下文，拥有独立 `system:data-grant:write`，并且目标在服务端策略可写范围内。组织管理员没有隐式写权。查看审计另需 `system:audit`，不随 grant 管理权附送。

平台运维需事先完成目标应用、精确 `resource:action` 菜单登记及 `DATA_GRANT_POLICY` 配置，明确哪些 scope 可以授予哪些业务组织。空策略默认拒绝。策略仍由服务端启动时读取，修改后须同步重启所有实例；管理页面不能编辑或热更新它。已有安装还需按[权限采用步骤](data-grant-management.md#安装独立管理权限)显式注册并授权新 MENU，不自动给全部用户开通入口。

## 1. 确认用户、组织和应用

确定普通用户实际使用的业务租户、组织和“工单管理”应用，并确认用户在该组织有有效直接成员关系，用户、租户、组织及祖先均有效。不要用祖先组织的成员代替目标成员，也不要把操作者当前的平台根组织当作业务归属。

如需创建或修复成员关系，由具有用户/成员管理权限的管理者通过已有页面处理。日常调整 data grant 不需要删除并重建成员；未改成员和 grant 会保留 UUID。

## 2. 完成功能权限链

在“授权管理”为目标租户、目标组织授权工单应用及本次需要的菜单/按钮；随后在“角色管理”配置角色菜单，在“用户管理”分配有效角色。每层都保留原有授权集合，只增减本次明确审阅的项目。

工单菜单登记可对照[应用 manifest](../business-apps/work-orders/deploy/bootstrap.manifest.json)：

| 需要的功能 | 精确权限或入口 |
| --- | --- |
| 进入工单 | `/micro/work-orders` 的应用根菜单 |
| 列表、详情读取 | `ticket:read`；详情菜单 `/micro/work-orders/tickets/:id` 可以保持隐藏 |
| 创建 | `ticket:create`；入口 `/micro/work-orders/ticket-create` |
| 更新、删除、导出 | 分别为 `ticket:update`、`ticket:delete`、`ticket:export` 的独立按钮 |

发送提醒的 `notification:publish` 是另一个独立权限，不因授权 ticket 操作自动获得。只授予当前职责需要的功能；应用已发布、用户有角色或某个菜单可见，都不会自动写入业务 grant。

## 3. 在“数据授权”选择精确目标

打开 `/system/data-grants`，也可从已有“授权管理”或“用户管理”的数据授权入口进入。入口仅在具备独立 read 权限时显示，路由仍校验精确 MENU 授权。没有用户目录或应用管理权限的 grant 管理者，也可以使用此页面的受限候选项。

先“选择数据授权应用”，再“搜索成员”，通过分页找到“名称 · 组织”对应的直接成员。页面不默认选择第一个应用或成员。核对用户、业务租户、组织和应用后读取当前授权；同名用户或同一用户的另一组织成员不能替代本次目标。

用户管理跳转可带 `userId` 筛选，服务端仍只返回该用户在当前可读边界内的有效候选项。修改地址参数不会授予越界目标；没有匹配项时应先核查授权和成员有效性，不能手填未经验证的 UUID 绕过选择。

## 4. 为所需操作选择已登记范围

当前表格分别显示已存 scope、有效范围及实际组织集合。只读管理者可核对这些信息；只有服务器确认目标可写、当前操作者具备平台根与独立 write 权限时才出现可提交的编辑控件。

对每个需要的 resource/action 选择“不授权”或服务端列出的 scope。例如策略已登记 `ticket:read` 允许 SELF、ORG 时：

| 选择 | 目标用户能读取的记录 |
| --- | --- |
| 不授权 | 缺少 `ticket:read` 数据授权，读取默认拒绝 |
| SELF | 目标用户拥有的记录，并叠加平台确认的组织上限；仅作为处理人不会扩大范围 |
| ORG | 当前目标组织中的记录 |

创建、更新、删除和导出分别核对自己的 `ticket:<action>` grant；读取范围不会代替其它操作的范围。未登记动作或 scope 不提供可选项；需要新增能力时由平台运维先审阅菜单和服务端策略，不能用请求参数临时扩大。scope 没有可推断的大小排序，也没有默认 TENANT。

pair 未登记或已存 scope 已不在当前允许列表时，页面标为“历史授权 · 当前不可编辑”，只显示已有记录，不进入差量。策略收紧不会自动删除这些业务授权；通过页面清理前，先由有权运维审阅并受控恢复该 pair 和已存 scope 的必要登记，再按正式预览/保存流程删除。

## 5. 预览后明确保存

点“预览变更”，逐项核对 `before`、`after` 与新增、更新、移除列表，尤其确认目标组织、精确 action 和实际有效范围。预览不会保存，也不预留后续写锁。

确认无误后点“确认保存”。页面提交刚才预览的精确差量与版本，不自动保存。改动选择后需要重新预览；没有实际差量时不发请求。修改已有 scope 和保留其它 grant 时不会更换其 UUID。

保存成功后记录页面显示的 requestId、目标和结果。切换应用、成员、组织或登录身份时，旧草稿和预览不继续用于新目标；迟到响应也不会填入新上下文。requestId 供审计关联使用，不是可以重复提交的幂等键。

## 6. 用普通用户验证并查询审计

让目标普通用户在其业务组织内使用自己的正常登录进入工单，发起新的列表、详情等受保护请求，验证所选范围。SELF 应只允许拥有且在组织上限内的记录，ORG 应限于目标组织。需要的功能按钮、读写和导出分别核对；不要用平台管理员身份替代普通用户验收。

下一次受保护新请求读取最新数据授权。已有页面可能需要发起新查询或按正常会话流程刷新授权视图；旧页面显示不能证明服务端仍允许访问。平台失联或无法证明授权时，业务请求继续按现有规则拒绝执行。

具备 `system:audit` 时，在保存结果处点“查询本次审计”。页面内按本次 requestId、目标应用、目标租户和 `DATA_GRANT_CHANGE` 精确查询，核对操作者与前后摘要。真实差量和审计同事务提交，审计失败会回滚；同值保存不会新增变更事件。没有审计权限时，可将安全 requestId 交给已获授权的审计人员核对。

## 7. 撤销并再次验证

重新选择相同应用和直接成员，将要撤销的 pair 设为“不授权”，再经过“预览变更”与“确认保存”。确认移除的是本次指定操作，其它未修改的 grant 保持。撤销 data grant 不需要删除用户、角色或成员。

随后让普通用户发起新的受保护请求，验证对应操作按缺失 grant 拒绝，或相关记录在列表、总数、详情、写入和导出中一致受限。若只撤销功能菜单，也应分别验证功能权限拒绝；菜单与 data grant 是两条独立链。保留这次撤销 requestId，并按上一步核对审计。

## 发生冲突、拒绝或结果未知时

| 页面结果 | 下一步 |
| --- | --- |
| “授权版本已变化，请重新读取并审阅” | 点“重新读取授权”，核对其他管理者的变更，重新编辑和预览；不把旧差量套上新版本直接提交 |
| 403 / 权限或目标失效 | 页面退出可写状态，清除草稿和预览，并隐藏旧快照、编辑和提交；核查当前权限、成员和策略，手动重新读取且 GET 获准后才恢复只读展示，当前编辑器仍禁止写入 |
| “保存结果待确认，请重新读取授权” | 网络错误、5xx 或回执不完整不能证明回滚。先重新读取当前状态，核对已存 scope/UUID/version，再决定新的差量并重新预览 |
| 可选应用或成员为空 | 核对实际上下文、独立 read、策略边界、目标有效性及应用授权；不要改用更宽的用户目录或 SQL 绕过 |
| 历史行不可编辑 | 交由有权运维审阅当前能力登记，再通过受控页面/API 清理 |

恢复读取前不重复点击保存；也不因换了 requestId 就假定可以安全重放旧意图。页面读取、预览、提交和审计都独立执行当前权限检查。
