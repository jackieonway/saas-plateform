# 登录准入、密码计算与来源身份

Phase 12 在现有 Rust 平台内增加进程级登录预算和统一异步密码服务。实现入口为 [login_limits.rs](../backend/src/login_limits.rs)、[password.rs](../backend/src/util/password.rs)、[client_ip.rs](../backend/src/client_ip.rs)、[Config](../backend/src/config.rs) 和 [AppState](../backend/src/state.rs)。本文描述源码契约；最终源码、实际测试、压力数据和限制以 [Phase 12 验证记录](validation/phase-12.md) 为准，当前声明不代表已完成实际验收。

## 默认配置与边界

配置在启动时校验，非法数值拒绝启动。下表单位为字节、毫秒、秒或条目，不根据宿主硬件自动放大。

| 环境变量 | 默认值 | 允许范围 | 含义 |
| --- | ---: | --- | --- |
| `PASSWORD_CONCURRENCY` | 2 | 1–32 | 同时持有执行许可的密码任务数 |
| `PASSWORD_QUEUE_CAPACITY` | 8 | 0–1024 | 执行名额之外的等待名额，可设 0 |
| `PASSWORD_QUEUE_TIMEOUT_MS` | 250 | 1–30000 | 等待执行许可的最长时间 |
| `PASSWORD_EXECUTION_TIMEOUT_MS` | 10000 | 1–120000 | 提交 blocking 任务后，调用者等待结果的最长时间 |
| `LOGIN_MAX_ENTRIES` | 4096 | 3–1000000 | 来源条目、输入标识条目和账号条目的共享上限 |
| `LOGIN_WINDOW_SECONDS` | 600 | 1–86400 | 从首次插入开始的固定窗口，使用单调时钟 |
| `LOGIN_SOURCE_REQUESTS` | 60 | 1–100000 | 每个来源每窗口的登录准入次数，成功也消耗 |
| `LOGIN_USER_FAILURES` | 5 | 1–1000 | 已记录失败达到此值后拒绝该输入/账号的新验密 |
| `LOGIN_IDENTIFIER_MAX_BYTES` | 320 | 1–1024 | 登录账号、电话或邮箱输入的原始 UTF-8 字节上限 |
| `LOGIN_VERIFY_BUDGET_MS` | 10000 | 1–120000 | 一次共享别名登录中全部候选账号验密的总预算 |

密码输入统一最多 1024 字节，超长输入在密码服务准入及复制前返回 400。验证路径也限制数据库 PHC 字符串最多 1024 字节，损坏或无法解析的 PHC 不视为验证成功。生产密码写入继续要求至少 12 个字符，拒绝已知演示密码、控制字符和纯空白；开发保留至少 6 字节的既有兼容规则。

这些配置只控制本进程。当前 Compose 声明一个平台 API 实例；使用默认值时，最多接纳 2 个执行任务和 8 个等待任务。N 个相同配置的 API 副本各持有独立预算，总密码执行/等待容量为单副本的 N 倍，登录条目容量和可分散的来源预算也随副本增加；进程重启清空本地计数。没有共享计数模式，不能声称跨副本固定全局配额。

多副本部署必须按实际副本数分配每进程预算并评估整个部署。本阶段不引入 Redis，不自动修改生产 Nginx 为共享限流，也不以单进程测试证明多副本全局限制。Compose 未显式透传的变量须由受审查的服务环境或 override 明确注入，不能只在宿主 `.env` 中写值后推断容器已采用。

## 有容量上限的登录状态

平台登录与 OAuth password grant 在查账号前，先按规范化来源消耗准入预算并预留输入条目；查到账号后，在验密前预留账号条目。不存在的随机账号也预留输入条目，避免并发请求等到验密结束后才计入容量。规范化登录输入先转 SHA-256，再拼接 `input:`，因此该调用键固定 70 字节，配置允许的 1024 字节输入或 Unicode 小写扩张不会撞上内部上限。limiter 键包含条目类别与固定长度摘要，内部仍保留 1024 字节的防御性标识上限；不会无限保存请求者输入的长字符串。

来源、输入与账号共用一个 `LOGIN_MAX_ENTRIES` 上限，过期索引每条记录恰好对应一项。重复访问不追加无界索引项；容量饱和时拒绝新身份，不驱逐仍在窗口内的身份，随机输入不能把已有账号的失败预算挤掉后重置。现有身份仍按原预算处理。

固定窗口从首次插入起计，不因持续失败延长。生产时钟使用 `Instant`；注入的时钟值也钳制到前次最大值，回拨不会重置窗口或造成时间下溢。每次操作从有序过期索引批量回收最多 32 条；目标键即使在这一批之外，到期后也会单独即时移除。这样在长时间空闲或大幅前跳后，单次清理工作仍有界。

成功验密只清除已证明账号及成功输入的失败预算，不补充来源准入次数。共享电话/邮箱登录只返回通过密码且有有效直接成员关系的账号；成功匹配其中一个账号不会给同别名的其它账号增加密码失败。全部未匹配时才记录本次失败。

共享别名最多查询 65 行并允许至多 64 个候选；超过上限要求使用其它登录标识。候选串行验证共用 `LOGIN_VERIFY_BUDGET_MS` 截止时间，任一等待或验证超时都拒绝本次登录，不返回已经验证一部分账号的部分 ticket。已启动的密码任务仍遵守下文的真实结束许可规则。

## 所有 HTTP 密码计算共用一个服务

同一个 `AppState.passwords` 服务覆盖平台登录、OAuth password grant、创建用户、管理员重置密码、本人修改密码，以及租户/组织 HTTP 创建流程中的联系人账号初始化。同步 `hash_password`/`verify_password` 只保留给服务启动种子、启动时演示凭据检测及测试，不参与 HTTP 请求计算；启动流程与 HTTP 服务预算分开。

本人改密在异步验证/计算后获取用户锁，再比较数据库密码 hash 与原证明一致，随后同事务替换密码并撤销平台会话，避免迟到的旧密码证明覆盖管理员并发重置。重置/改密继续遵循原有撤销范围：旧平台 session 失效，旧密码不能再新签普通 OAuth；已经签发的普通 OAuth 凭据不因此自动撤销，仍按 Phase 11 实时状态和显式 revoke 契约处理。本阶段不扩大普通 OAuth 的撤销策略。

服务先以非等待方式取得总准入许可，再限时等待执行许可；获得执行许可后才复制任务需要的密码/PHC 字符串并交给 `spawn_blocking`。CPU 工作离开 Tokio 异步执行线程，密码队列不会无限增长。

```text
校验输入 → 总准入许可（执行 + 等待） → 限时等待执行许可
         → spawn_blocking（两项许可移交任务） → 实际计算结束释放许可
```

队列满、队列超时或执行等待超时返回 HTTP 429 与 `Retry-After: 1`；平台使用既有 `TOO_MANY_REQUESTS` JSON，OAuth password 使用 `temporarily_unavailable` 协议错误。登录来源/失败预算的拒绝也返回 429，重试提示按窗口剩余时间计算。

`PASSWORD_EXECUTION_TIMEOUT_MS` 包含提交任务后等待 Tokio blocking 线程池的时间。它是响应等待预算，不能终止 Argon2，也不证明计算已经结束。客户端取消、连接关闭或执行超时后，后台任务继续持有总准入和执行许可直到真实退出；后续请求不能利用响应超时提前复用正在占用的 CPU 名额。超时后的密码变更不会因为后台 hash 晚到而继续执行后续数据库写入。

新 hash 继续使用 `Argon2::default()`：Argon2id v19、`m=19456 KiB`、`t=2`、`p=1`，没有降低密码算法成本或生产强度策略。验证沿用已存 PHC 的参数以兼容旧 hash；非默认参数的内存/CPU 成本没有被本次默认配置测量覆盖。并发许可限制任务数量，不等于限制任意 PHC 的单任务内存；实际容量必须结合已有 hash 参数、运行环境和阶段报告判断，不能从默认 2 个任务推导通用内存或吞吐保证。

## 来源地址的可信边界

`normalize_client_ip` 在路由和审计之前根据真实 socket peer 解析一次来源，登录与既有 OAuth 限流使用同一个结果。`TRUSTED_PROXY_IPS` 只允许精确 IP，没有通配或 CIDR。规则为：

1. socket peer 不在精确信任表时，只使用该 peer，忽略来访者自填的全部代理头。
2. peer 是可信代理且带 `X-Forwarded-For` 时，从真实 peer 开始由右向左剥离可信代理，停在最近的非可信地址。其左侧可能由客户端伪造，不能直接使用最左项。
3. 可信 peer 没有 XFF 时，才接受其覆盖写入的单个合法 `X-Real-IP`。XFF 存在但非法、重复、过长或含空项时回退 peer，不再尝试另一个来访者头。
4. 无真实 peer 的进程内请求统一使用 `unknown` 来源桶，不能靠构造头绕过预算。IPv4-mapped IPv6 转为规范 IPv4，避免同一地址得到两套计数。

XFF 解析最多 2048 字节、32 跳，重复 header、非法 IP、端口混入或非文本输入都不能选择来源。中间件随后删除外部 `Forwarded`、XFF 和原 `X-Real-IP`，只写入已规范化的 `X-Real-IP` 供 handler 和审计消费。可信代理本身仍应覆盖/受控追加来源头，且 API 私网入口不得暴露给能冒充可信 peer 的路径。

## 验证与采用

当前 fast 声明 27 步，包含登录 limiter 8 项、密码服务 8 项、client IP 6 项及 config 4 项单元测试；完整清单由 [run.mjs](../scripts/ci/run.mjs) 决定。PostgreSQL manifest 当前八组 46 项，在 Phase 11 七组 41 项基础上增加 `login_protection_tests` 5 项，覆盖随机账号/来源伪造、共享别名、聚合截止、创建/改密/重置/OAuth 生命周期和混合密码压力下的健康/受保护读请求。

node scripts/ci/linux-runner.mjs --gate fast --image saas-ci:phase04-tools --out-dir /absolute/new-report/phase12-fast

这些命令只面向隔离测试环境。实际通过、失败、跳过、硬件与压力数据以 [Phase 12 报告](validation/phase-12.md) 为准；声明不等于测试已运行。采用时核对可信代理地址、容器实际环境和 API 副本数，再按同一源码运行必要门禁。本阶段没有数据库迁移，也不改变 Phase 11 的 OAuth 存储/单次消费或平台 `psr_`、应用 token 协议。
