# Phase 11 业务试点提案：工单管理

> 状态：用户已于 2026-10-02 确认采用本提案，作为 Phase 11 实施范围。代码与验收尚待完成，本提案不作为 Phase 11 已完成的证据。

## 目标与交付

使用有真实 PostgreSQL 持久数据的最小工单模块验证 SaaS 授权、独立微前端、独立业务 API、版本发布与通知。建议应用编码 `work-orders`，Vue 前端使用默认 iframe 和平台 SDK；Node 24 业务后端使用机密客户端逐请求内省及当前应用上下文，不共享平台 JWT 密钥。平台与业务应用可各自部署。

前端产物、业务 API、数据库迁移、环境配置、独立版本注册清单、两租户端到端测试和操作说明一并交付。试点采用业务后端自己的 PostgreSQL 表和连接配置；平台继续管理用户、租户、组织、角色、独立数据授权及通知。

## 业务字段

| 字段 | 规则 |
| --- | --- |
| 工单 ID／编号 | 服务端生成，租户内唯一；资源 ID 不充当授权依据 |
| 标题 | 必填，最多 200 字符 |
| 描述 | 可选，最多 8192 字符，纯文本 |
| 优先级 | LOW、NORMAL、HIGH，缺省 NORMAL |
| 状态 | OPEN、IN_PROGRESS、RESOLVED；创建为 OPEN |
| 创建人／数据归属人 | 服务端取当前用户，客户端不能覆盖 |
| 所属租户／组织 | 创建时取经验证的应用上下文，客户端不能改租户或搬移组织 |
| 处理人 | 可选，必须是该工单所属组织的有效直接成员 |
| 创建／更新时间、版本 | 服务端生成；更新按版本控制，拒绝覆盖别人已提交的修改 |
| 删除标记 | 软删除；列表、详情、写入和导出均排除已删除行 |

首版不增加附件、支付、复杂审批或跨组织搬单。删除记录保留在业务库且不自动清理；正式保留期另待业务方确认，测试库和测试数据按隔离验收流程清理。

## 操作流程

1. 用户登录平台并进入直接加入的组织，打开已授权的工单应用。
2. 按授权列表查看工单、筛选状态／优先级；有创建权限和数据授权的用户创建工单。
3. 有更新权限和数据范围的用户修改标题、描述、处理人、优先级或状态。允许 OPEN→IN_PROGRESS→RESOLVED，也允许 RESOLVED→IN_PROGRESS 重开。
4. 删除为软删除；CSV 导出使用独立导出权限与数据授权，并处理电子表格公式字符。
5. 工单详情提供独立的“发送提醒”动作。发布者必须同时具有通知操作权限和对应独立数据授权，目标为当前范围内有效且可访问本应用的成员。提醒链接指向本工单，失败重试使用同一业务事件键；发送提醒不重复保存工单。
6. 用户在宿主收件箱查看提醒并标记已读。仅弹 Toast 的展示回调继续使用 `onNotify`。

## 角色与独立数据授权

角色控制 `ticket:read/create/update/delete/export` 操作，数据范围由当前组织成员的 `ticket/read/create/update/delete/export` 显式 grant 决定。没有对应 grant 就拒绝。通知另使用已经确认的 `notification:publish` 与 `notification/publish` grant。

| 数据范围 | 工单读取／更新／删除／导出范围 |
| --- | --- |
| SELF | **创建人／归属人是当前用户**的工单；处理人身份本身不扩大范围 |
| ORG | 当前组织的工单 |
| ORG_SUBTREE | 当前组织及有效子组织的工单 |
| TENANT | 当前租户的工单 |

创建始终写入当前上下文组织，归属人始终是当前用户。较大数据 grant 允许访问已有记录，不自动授予进入其它组织的资格。权限和资源归属由业务 API 验证，界面按钮只表示可用操作。

## 验收场景

- 两个租户、各含父子组织与不同成员，数据库和服务端查询证明彼此隔离。
- 四级范围分别覆盖列表、详情、写入、软删除和 CSV；篡改租户／组织／资源 ID、绕过隐藏按钮、未授权操作均拒绝。
- 角色继承只扩展功能权限，不能扩展独立数据范围。
- 组织切换、成员移除、授权撤销和旧令牌不能继续访问业务 API；迟到请求不显示旧组织数据。
- 工单提醒真实入平台库、当前收件箱及 Socket.IO，去重重试不生成重复收件行。
- 独立前端 v1→v2→回滚 v1 不重建宿主；业务 API 与平台授权保持一致。
