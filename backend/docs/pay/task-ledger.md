# 支付应用实施台账

## 1. 项目目标、当前事实与执行指针

本台账是未来独立支付应用的执行依据，覆盖账户组织共享、普通收款、退款、可靠任务、公开客户端和历史迁移。当前六个独立仓库没有支付工程、支付数据库或渠道接管服务，本文不描述已部署支付能力。

| 状态项目 | 当前值 |
| --- | --- |
| 当前阶段 | 阶段 1：核对源码基线并冻结首期合同 |
| 当前目标 | 后续收到具体执行请求后，先只读核对来源并冻结首期输入 |
| 一期状态 | 45 个阶段全部 NOT_STARTED |
| 扩展状态 | E01～E09 全部 NOT_STARTED |
| 本次工作范围 | 仅重写文档；没有执行任何支付阶段 |
| 拟建工程 | 独立 saas-payments 仓库，最终名称、appCode、basePath 在阶段 1 冻结 |

本文所有 saas-payments/ 路径均相对于六仓库所在的工作区父目录，属于未来产物，不存在的平台 .integration 业务目录不再作为代码位置。支付身份、数据库和发布链路必须独立；其他业务仓库的测试通过不能代替支付验收。

一期成功要求所有冻结必需场景达到本台账的验收终态，资金事实、原账户、授权范围和恢复义务均有实际证据。全量替代还需交接全部 E 项及未结清义务；一期通过不能用于自动停用旧系统。

方案概览见[支付规划](README.md)，平台现状见[文档索引](../README.md)和[整体架构](../architecture.md)。阶段推进必须更新状态、依赖、证据与下一指针，不能从文档生成推断实现完成。

## 2. 全局约束

### 技术和数据库选择

- G01：生产后端采用 Rust，优先复用 Axum/Tokio/SQLx/Reqwest/Serde/Tracing 经验；管理端独立采用 Vite/React/TypeScript，支付宝客户端保留原生 TypeScript。
- 新支付库建议 PostgreSQL 17，是否保留MySQL双库必须在Q08冻结；旧Java维护期仍遵守原双库规范。数据库、HTTP与秘密策略独立验证。
- Node只用于前端/测试/构建发布工具；不引入Node生产业务后端、Bun、Caddy或Next.js。以实际仓库工具链和锁文件为基线，不顺手升级。

### 独立部署、qiankun 和平台身份

- G02：支付 API、worker、数据库及静态前端各自部署；支付数据库账号不能读取平台身份表，不依赖平台、门店、工单业务实现 crate，领域规则不依赖 HTTP、SQL 或具体渠道实现。
- 管理端使用 qiankun HTML/TRUSTED 和固定 SDK 2.0.0，按新应用接入合同导出 bootstrap/mount/update/unmount 四个生命周期，通过 props.platform、props.services 和本次 container 接受宿主上下文。公开收银台使用独立入口与受限身份，不能借管理页面扩大资金操作权限。
- 当前平台已有可选镜像部署与 ZIP 分发能力，但支付尚未接入。支付的 KnownApp、网关、镜像及发布策略扩展仍属于后续实现。
- G03：平台是管理用户、密码、登录、账号、成员和角色的唯一身份来源。支付只保存必要 UUID、最少快照及业务关联；用户管理仍用宿主 session 与系统权限，应用 token 不替代管理 session。
- combined 使用 Basic + form(token/resource/action)；legacy显式配置，不失败自动回退。每请求重验并独立核对完整合同；不缓存正向授权。

平台permission严格是小写资源动作的 `resource:action`，例如建议 `pay-account:use` 对应账户使用，`pay-account:read/create/update` 对应管理动作，`pay-account-grant:read/create/update/revoke` 对应分享规则维护。USE/MANAGE/SHARE是本文业务能力术语，不直接作为大写平台action；最终资源清单在阶段 1与原方案的pay-merchant等命名统一冻结，客户端/菜单/capabilities/接口使用同一清单。

### 订单身份、资金事实和原账户

- G04：租户必须硬隔离，真实来源组织不能由前端伪造或普通编辑。支付商户、渠道账户、服务商应用、管理用户和渠道付款人分别建模。
- 一个逻辑业务订单一个意图、多个渠道尝试、一个有效收款。默认唯一键tenant/source/businessOrderId；源业务命名空间例外必须冻结，merchant/channel不是意图身份。
- 每attempt保存实际商户、原渠道账户/应用与版本；查关退与恢复沿原账户。配置版本与合法秘密轮换分开，未知历史版本不能由当前绑定补造。
- 金额用检查过的整数最小单位/明确十进制，费率和舍入规则固定；旧无时区时间先确认来源时区，大ID用字符串。
- G05：渠道超时、HTTP 取消和数据库提交丢确认都可能已经发生资金动作；只能沿原稳定事件/渠道号查询，不能换号重复扣退。不同退款号共用原支付总额度，处理中与未知退款均继续占用。
- G06：真实收款事实不因异常回滚或乱序被覆盖，多笔成功全部保存。重复成功产生唯一的原路退款义务，实际退回前不能标已退；普通收款与免押使用独立生命周期。

### 动态组织子树与账户使用合同

1. G07：同租户根组织或中间组织可以拥有账户，并显式授予本组织或组织子树 USE。owner 保持不变，渠道秘密留在服务端，不通过复制账户实现共享。
2. USE只表示按获准商户/场景等约束使用收款资源；MANAGE维护允许的账户配置；SHARE维护授权受众。三者分别授权。USE/MANAGE均不能自动推导SHARE或向下继续转授。
3. 建议默认创建只给本组织使用；可选择“本组织及全部下级”或“指定子树”。产品如要求创建即全树可用，也必须在同事务显式生成可见、可撤销、可审计规则。Q03尚待冻结，不能把建议当已批准默认。
4. 子树规则包含锚点本组织与当前/未来有效后代，使用权动态计算；不按授权时静态展开ID列表冒充动态继承。首版默认不实现下级转授或复杂排除规则；有新要求先冻结合同。
5. G08：下级获得的是当前业务组织的账户使用关联，不能因此获得祖先账户的管理数据。可用账户只返回最小字段，管理列表仍按 owner/管理范围；禁止把父组织塞入 context 扩大可见性。
6. 可信关系由平台窄用途合同或经批准的等价机制提供，不直查平台库、不相信前端parent/path。用户关系证明与机器关系证明分别认证；全局应用Basic不能自行访问任意租户组织。
7. 每次新受理同时满足平台身份/功能permission/数据授权、组织硬上限、账户使用规则、账户状态及交易约束。业务API则满足获准机器租户/来源/组织和同一账户策略；付款会话只引用已受理的归属。
8. 至少一条完整有效USE路径覆盖目标组织、动作/场景、期限和限额；不能从不同规则各取宽松条件拼接放行。系统硬限额继续收窄。撤销一条规则后不能再借该规则放行；另有独立有效授权时按其判断，无有效规则时拒绝。
9. G09：后代新增后在下一次权威检查自动继承资格；未来移出/移入按当前关系重算。当前不新增平台组织移动 API，重挂语义只用受控 fixture 验证；已有新增、启停操作通过正式 API。
10. 规则/账户撤销或关系链停用阻止后续新受理；已受理交易继续原账户回调、查补及批准意图恢复。平台核验到支付库COMMIT仍有跨库竞态，默认不承诺全局原子强撤销。
11. G10：每笔交易属于实际来源组织，共用账户不允许兄弟组织互查订单。总部读取下级仍需交易 permission/grant；真实结算沿渠道账户或子商户合同，不自动分账，也不自动赋予各组织独立余额或银行入账。
12. 只有明确批准的同租户共享属于本期；平台根跨租户共享/运营是新能力，不以admin/super标志关闭tenant过滤。

账户规则的ORG/ORG_SUBTREE表示受众覆盖方式；平台数据授权的scope表示当前用户对某资源动作的数据范围。两者是独立授权条件。账户使用用途按业务发起组织/使用关联核验平台范围，账户管理用途按owner/管理范围核验，不能要求下级拥有祖先账户的通用管理读取权限才能使用。

### 四类非管理身份、回调和恢复

- G11：商户/业务客户端、付款会话、渠道回调和 worker 分别使用自身身份与准入；后台不能长期保存用户 token，openid 也不是管理 userId。
- 商户签名含明确版本/编码/时间窗/nonce，多副本防重放与资金幂等分开。通知目标、订单provider及跳转地址由服务端批准，拒绝任意URL与无控制redirect。
- 回调保留验签必需原字节，先验证、可靠收件再按渠道合同ACK；inbox/outbox/任务及其状态可恢复。共享账户加密回调先可信提取稳定单号，再查owner，不广播两个引擎。
- 导入或隔离恢复时保留原业务状态，另设全部可执行任务的迁移禁用门禁；jobs/outbox/商户通知/查补/退款均不能自动领取。演练出口仅受控fixture，owner和允许操作核对后才显式激活，不能误投旧生产notifyUrl。
- G12：秘密不得进入代码、文档、日志或前端产物；必要原文加密并限期保存。业务写与审计同事务，actor 区分管理用户/client/渠道/worker，用户删除不能级联移除交易。
- 真实资金、生产发布或第三方上线必须有具体获准操作域；创建台账只授权当前文档交付，不推导后续动作已批准。

### 工程边界、迁移和证据

- G13：按适用 AGENTS 保持单 crate 模块优先、薄入口厚库、依赖单向和公共 API 收敛；缺乏稳定复用依据时，不提前建立公共 crate 或 workspace。
- 每阶段使用实际manifest进行fmt/check/clippy/test/doc及相称数据库/协议/浏览器验证；可执行的根命令要以真实工程形态为准。不能把未运行、失败或必需skip写成通过。
- 不改已执行迁移checksum；新schema用追加迁移，Flyway/SQLx历史不可直接互认。恢复需兼容构建，数据库回退不撤销渠道事实。
- 每阶段保留源码/产物摘要、环境/工具版本、执行命令、通过/失败/未运行、限制、清理与恢复记录。建议证据为 backend/docs/pay/validation/phase-NN.md，均为未来拟产出。

### 当前执行范围与禁止捷径

- G14：本轮只重写支付规划，不执行任何一期阶段，不创建支付代码或数据库，不调用渠道，不发布镜像或小程序。
- 不按旧admin、重名、相同邮箱/电话自动合并或授权；不把当前导入人补为历史owner。
- 不关闭tenant/组织过滤来支持账户共享；不复制父账户密钥给下级；不让USE拥有转授、退款或转账权。
- 不在渠道HTTP时持长数据库锁，不依靠进程Mutex保证多副本安全，不以lease撤销已发请求。
- 不让旧新引擎同时写同单，不自动换渠道号恢复未知资金事件，不无条件广播回调，不以快照覆盖已发生资金事实。
- 不启动E01—E09整包；先根据实际范围细分成满足本台账格式的可执行阶段，并更新依赖/指针。未迁移能力不能悄悄停用其旧处理方。

### 阶段状态的维护规则

阶段只使用 未开始（`NOT_STARTED`）、进行中（`IN_PROGRESS`）、受阻（`BLOCKED`）、已完成（`COMPLETED`）。当前全为未开始（`NOT_STARTED`）；文档创建不是某个支付实现阶段完成的证据。Q表的OPEN是问题状态，不是第五种执行阶段状态。

未来只有在收到执行请求且本阶段前置终态/外部输入满足后才进入进行中（`IN_PROGRESS`）。遇到真实必需外部阻碍，记录已完成准备、具体阻碍和恢复条件；未执行的当前创建阶段不预先标受阻（`BLOCKED`）。必需验收未通过不得已完成（`COMPLETED`），预算或输出文件存在不替代终态。

阶段完成时同步汇总、详情状态、当前指针、决策/变更和证据。当前默认按编号前进；只有依赖满足且用户授权范围允许时才并行。不得为追赶数量改变合同、删除必需验收或跨阶段偷偷实现后续内容。
