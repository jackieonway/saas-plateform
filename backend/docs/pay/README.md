# 支付应用方案（未实施）

## 当前事实

现有体系包含平台、工单、门店、通知、SDK 和示例六仓库，没有 payments 工程、支付业务库或已接入渠道的支付服务。平台现有身份/授权与应用发布能力可以作为未来接入基础，不能直接当成完整支付系统。

本方案独立于当前开发和部署指南；它不提供可直接运行的支付 Compose，也不代表已批准调用真实资金渠道。

## 目标架构

未来支付应用按独立仓库组织管理微应用、Rust API/工作进程、专属数据库；公开 WAP 收银台和支付宝原生小程序使用单独入口。平台管理身份、租户、组织和授权，支付域保存商户、账户、交易、退款、事件和账户共享规则。

管理端通过登记 SDK 与 opaque iframe 接入；公开付款不能通过放宽管理 iframe 的同源、顶层导航或弹窗权限实现。业务服务通过平台 HTTP 获取身份与组织关系，不读平台用户表、不依赖平台业务实现 crate。

## 必须冻结的业务边界

- 一个逻辑订单一个意图、多个渠道尝试，只能有一个有效收款；重复成功事实和退款义务不能丢失。
- 超时、取消、提交回执丢失均可能已产生资金动作，沿稳定事件/渠道号查询，不生成新号重复扣退。
- 金额使用受检查的最小单位或明确十进制，交易保存真实来源组织及原渠道账户版本；后续查关退沿原账户。
- 账户使用、管理、分享分开授权。同租户根/中间组织可显式授予组织子树使用，账户 owner 和秘密不复制。
- 子组织获得最小可用账户投影，不得到祖先管理数据或兄弟交易。平台权限、数据授权、当前关系、账户规则和交易约束同时满足才受理。
- 撤销阻止新受理，已受理交易保留原账户恢复与回调责任；不承诺平台库和支付库全局原子撤销。
- 旧系统的余额、冻结、转账、付款、免押等未接管能力保持明确处理方，普通支付一期验收不等于旧系统可全退役。

## 实施顺序

先核对 UnifyPay、QuickPay 的真实源码、缺失接口、生产数据与渠道合同，冻结一期范围和命名；再建立 Rust 工程、平台应用与组织关系协议，实施账户/共享授权、交易与可靠任务、退款、公开客户端及迁移验收。

已有 [实施台账](task-ledger.md)保留 45 个一期阶段、全局约束、扩展义务与待确认输入，全部未开始。每阶段要有实际证据才能推进；不能用文档、模拟成功或当前工单/门店验收替代真实支付结果。

生产域名、渠道账号/证书、客户身份映射、旧订单归属、审计留存、灰度和 RPO/RTO 需要单独确认。支付实现被明确启动后再编写对应工程的开发/部署操作文档。
