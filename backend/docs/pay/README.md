# 支付应用规划

支付应用尚未实施。当前工作区已有平台、工单、门店、通知、微应用 SDK 和示例六个独立仓库，没有支付工程、支付业务数据库或已接管渠道的支付服务。本文和[实施台账](task-ledger.md)保留未来建设要求，不能作为已部署能力、渠道开通或生产操作授权的证明。

## 规划目标与工程边界

目标是将旧支付管理、普通收款、退款、通知和迁移能力逐步迁入独立 Rust 支付域，保持真实资金事实、历史账户证据和未结清义务可追踪。拟采用独立仓库 `saas-payments`，名称、应用编码和路由须在阶段 1 冻结；不再使用平台 `backend/.integration` 承载业务工程。

| 单元 | 拟定职责 | 身份与数据边界 |
| --- | --- | --- |
| 支付管理微应用 | 账户、共享规则、交易、退款及运维界面 | qiankun HTML/TRUSTED，消费固定 SDK 2.0.0，使用平台用户和当前组织授权 |
| Rust API 与 worker | 账户策略、交易状态、渠道适配、可靠任务 | 支付专属数据库，不查询平台身份表，不依赖其他业务实现 crate |
| 公开 WAP 收银台 | 受限付款会话、OAuth、渠道调起和结果恢复 | 独立公开入口，不接收管理令牌，不以客户端结果认定到账 |
| 支付宝原生小程序 | authCode、LITE 场景、tradePay 和服务端回查 | 保留原生 TypeScript，发布凭据留在受控发布环境 |

平台继续管理登录、租户、组织、成员、角色、功能权限和数据授权；支付域只保存必要的平台 UUID、最小快照及支付业务关联。平台核验与支付库提交存在跨库竞态，设计必须说明边界，不能承诺尚未实现的全局原子撤销。

## 管理端接入采用 qiankun 与 SDK 2

未来管理端必须按平台新应用接入合同导出 `bootstrap`、`mount`、`update`、`unmount` 四个 qiankun 生命周期，`update` 负责接收新令牌、组织、权限和路由上下文。宿主通过 props 的 `platform` 交付 MicroProps 2.0，通过 `services` 交付宿主能力；子应用使用本次 `container`，独立释放事件、订阅、定时器和请求。产物必须是 HTML 加经典脚本/UMD，不能直接交付 Vite 默认的 module 脚本。

接入使用可信运行模式，子应用代码在宿主页面内执行，必须经审核和固定交付。平台可按环境登记直接 URL 并启用同域资源代理，或检查并激活版本入口；资源代理不能代替业务 API 的身份验证。SDK 客户端使用当前应用受众令牌、`credentials: omit` 和宿主取消信号，组织切换、撤权、更新及卸载后拒绝旧响应。

公开收银台、付款人 OAuth 和原生小程序使用各自的受限身份链，不通过管理端沙箱扩大权限来实现支付调起。旧 opaque iframe、Origin 为 null 的桥接协议不再是支付管理端的目标方案。现行接入合同见[微应用接入](../micro-application-onboarding.md)和[应用授权协议](../application-authorization-contract.md)。

## 资金与组织授权的不变量

- 一个逻辑订单对应一个支付意图，可以有多个渠道尝试，只能有一个有效收款。所有真实成功事实仍须保存；重复成功产生独立、唯一、可恢复的原路退款义务。
- 超时、取消、连接中断或提交回执丢失都可能已产生资金动作。恢复必须沿原事件键、原渠道单号和原账户版本查询，不能换号重复扣款或退款。
- 金额采用受检查的最小单位或明确十进制。交易记录真实来源租户/组织、商户、渠道账户和配置版本，后续查询、关闭、退款和恢复沿原账户执行。
- 账户 USE、MANAGE、SHARE 分别授权。同一租户根组织或中间组织可显式授权本组织或组织子树使用；owner 和渠道秘密留在原账户，子组织只取得最小可用投影。
- 每次新受理同时检查平台身份、功能权限、数据授权、组织范围、完整有效的账户使用规则、账户状态和交易约束。共享账户不授予兄弟组织交易读取权，也不自动改变真实资金结算主体。
- 撤销阻止后续新受理，已受理交易保留回调、查补和批准恢复责任。账户规则受众、用户数据范围和机器准入是独立条件，不能相互替代。
- 回调可靠收件、事务 outbox、退款额度预占、幂等、审计与恢复必须形成完整闭环。导入和恢复批次默认禁用一切外部执行，核对 owner 和允许操作后才明确激活。

这些约束及其编号化要求完整保存在台账。旧系统余额、冻结、转账、充值、免押等能力尚未接管时，必须保留真实处理引擎和责任人，普通收款一期通过不能作为旧系统全量退役的依据。

## 实施路线与状态

一期保留 45 个阶段，全部为 `NOT_STARTED`，当前执行指针仍为阶段 1。本次只更新文档，不启动任何阶段。未来执行时，以台账的输入门禁、前置依赖、交付物和验收标准为准：

| 阶段 | 主题 |
| --- | --- |
| 1～4 | 核对旧源码/合同，建立独立工程与平台授权、可信组织关系 |
| 5～11 | 账户、动态子树使用授权、管理微应用和隔离部署 |
| 12～17 | 机器准入、权威订单、渠道适配与持久资金意图 |
| 18～25 | 四类收款场景、查关单、回调、worker 与商户通知 |
| 26～33 | 退款、重复收款裁决、公开会话、OAuth、WAP 和小程序 |
| 34～39 | 管理页面、历史证据、隔离导入和新旧引擎 owner 分发 |
| 40～45 | CI、恢复、容量、真实渠道验收、获准灰度和一期交接 |

E01～E09 保留余额账本、转账、充值、余额付款、进件、发货、支付宝免押、微信支付分、完整对账等未来扩展。它们要先细分为可执行阶段再推进，不因本期未实施而删除。

## 实施前仍需冻结的输入

台账 Q01～Q21 记录完整问题和受影响阶段，包含旧客户/订单归属、账户对象、共享默认、真实结算主体、缺失订单服务、单号命名空间、数据库兼容、渠道模式、机器准入、退款复核、兼容期限、历史账户证据、用户映射、在途义务、渠道测试条件、容量与 RPO/RTO、留存、发布操作域及新旧回调分发。

阶段 1 可以先做获准源码和配置的只读核对；必需输入未满足时，后续依赖动作不能被标为完成。真实资金、生产发布和小程序上线需要具体允许的环境、额度、对象及操作范围；当前文档任务没有授予这些动作。未来阶段完成时，必须记录实际源码/产物摘要、环境、命令、通过/失败/未运行及恢复清理证据。
