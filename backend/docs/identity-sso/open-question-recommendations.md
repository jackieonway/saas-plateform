# 员工／客户身份与 SSO：新库实施建议

> 2026-10-24，实施同步 v0.5。依据用户“新库新开功能，旧数据不涉及，其余问题先给建议”的说明，以及[主方案](README.md)、[实施台账](task-ledger.md)和关联聊天《设计员工与客户身份模型》。Phase 1 的成员／准入 schema、显式生命周期及默认关闭的配置已经实现，实际基线和回归结果见[阶段证据](validation/phase-01.md)；下一实施入口为 Phase 2，正式状态以台账为准。本文中的生产域名、客户端、容量与恢复建议仍是候选，不能按实现了 Phase 1 推断已经配置或达标。预览 UUID 专项独立维护状态。

## 1. 已确认范围与建议的区别

- **用户已确认**：本次身份新功能使用新库，没有需要归类、合并、迁入或恢复使用的历史账号、身份和凭据。同账号同组织可以同时拥有员工和客户两条独立成员关系，客户不进入 RBAC。
- **本文建议**：组织绑定规则、首版功能、开发域名和客户端划分、兼容范围、容量与恢复目标、工程位置和通知规则。具体建议见下文，不将建议当成已经确认的生产配置。
- **另一任务的范围**：关联聊天仍在执行本地预览三库的 UUID 保数据专项。本轮的新功能范围说明不自动取消、改写或接管该任务，也不把它的历史数据要求继续施加到本身份新库上。

新库范围消除了历史数据处理，仍须完成 UUID v7、逐请求权威身份校验、同组织双身份隔离、局部撤销及应用／客户端准入验证。

## 2. 开放问题逐项建议

| 问题 | 建议处理 | 对实施的影响 |
| --- | --- | --- |
| Q1 历史账号与客户分类 | 在本身份新库范围登记为“不适用：用户已确认无历史数据”；不设计旧账号分类、手机号／邮箱合并或旧成员回填任务。 | 不阻止 Phase 1；新建成员仍须显式类型和精确账号绑定。 |
| Q2 客户组织归属 | 有权限管理员显式选择当前租户内已存在、有效的组织。跨组织客户分别建立 CUSTOMER 成员关系；同组织 EMPLOYEE／CUSTOMER 各最多一行。 | 作为创建 API 与组织选择 UI 的默认规则；具体归属组织在每次创建时确定。 |
| Q3 首个客户业务 | 首版仅实现当前客户 context、本人基础资料，以及按已登记准入筛选的应用目录。 | 不扩展订单、工单、积分或客户资产；真实业务另立资源与动作合同。 |
| Q4 域名、issuer 与回调 | 开发使用三个独立 HTTPS origin 与两个独立 BFF 客户端；生产在自有主域下使用同样拓扑。精确建议见第 4 节。 | Phase 1～6 无需生产域名；实际 OIDC 接入前固定对应环境的 issuer 与回调。 |
| Q5 旧客户端与退役 | 本新库不迁移旧凭据、不安排历史用户转换窗口。保留现有活动 SDK、员工应用与机器服务协议；新 USER client 默认只开 code＋S256。 | 保留消费者合同验证；新部署默认关闭无人使用的旧 grant，不因新库删除跨仓服务合同。 |
| Q6 容量、超时与可用性 | 使用第 5 节的隔离压测假设和现有 3 秒业务鉴权预算，生产可用性候选为月度 99.9%。 | 先建立测量；建议值不算压测通过或上线承诺。 |
| Q7 备份与恢复 | 内部试运行候选 RPO≤24h、RTO≤4h；生产候选 RPO≤15min、RTO≤60min，后者须增加 WAL/PITR 并演练。 | 当前工具不具备 PITR 证明；恢复后撤销旧凭据再开放流量。 |
| Q8 工程位置与归属 | Phase 7～10 先在现有平台内建立模块与 port；Phase 11 新建客户门户独立仓库，Phase 12 再拆独立身份服务。 | 建议路径见第 7 节；本轮不创建工程或指派不存在的维护人。 |
| Q9 客户通知与归档 | 首版不开放客户通知；缺省／现有广播的目标合同为仅有效员工，Phase 4 实现具体成员与身份版本隔离。 | Phase 1 未完成通知各通道隔离；客户创建继续关闭，Phase 4 仍为必需阶段。 |
| Q10 同组织双身份 | 沿用已确认的两条独立成员关系、最终三元唯一键、独立 ID／状态／版本。 | 每次请求只用一个明确 membership；切换不原地改 member_type。 |
| Q11 UUID 旧库重建与映射 | 本身份新库的历史重编号、外部旧主体映射和保数据导入不适用；以第 3 节的新库基线证据替代。 | 不将 UUID-U03～U06 假标完成；另一个预览库专项保持自己的状态与范围。 |

“不适用”是开放问题的范围结论，不是新增的阶段状态。阶段仍使用原台账的 NOT_STARTED／IN_PROGRESS／BLOCKED／COMPLETED。

## 3. 新库前置条件与台账冲突处理

### 3.1 已实施的空库 UUID v7 基线

身份新库无需历史导出、旧→新映射或保数据切流。[空库 v7 基线](validation/fresh-v7-baseline.md)已经形成，涵盖真实 SQLx 全链迁移、当前 seed 及幂等、v7 UUID 约束与引用、活动 SDK 3.0 和门店／工单授权消费单测。成员生命周期及 v12 员工 fixture 升级的最终命令、结果与限制统一见[Phase 1 验收](validation/phase-01.md)。

该基线保持以下要求，后续阶段不得破坏：

1. 明确登记隔离的新目标库，从空库真实执行已有迁移链和 seed；保留历史迁移字节，采用追加迁移演进。
2. 系统自有 UUID 主键与引用、生产发号入口、seed 和活动消费者使用 v7；最终 schema 不依赖 v4 默认。历史迁移、历史发行字节及 v4 负例不因保留而算失败。
3. 生成与输入校验、外键和自然键、应用／客户端配置、活动 SDK／业务服务合同有实际验证；secret、code、refresh、nonce 等安全随机材料继续使用 CSPRNG，密码哈希维持现有安全要求；UUID v7 只替代系统标识生成。
4. 测试使用明确标注的账号与成员 fixtures，不读取、转换或借用预览库旧主体。新环境从空会话开始，不恢复旧 token。
5. Phase 1 已追加成员／准入扩展迁移，保留二元及三元唯一约束，该阶段开关仅允许隔离 `APP_ENV=test` 且应用环境非 production 验证。生命周期／客户／第二身份开关当前仍默认关闭；现行[Phase 6 独立收缩与启用合同](phase-06-rollout.md)保留 fixture 分支，其他环境须提供环境绑定的 receipt 与 manifest 摘要并通过启动验证。[Phase 6](validation/phase-06.md)已完成任务自有 development 验收，生产未启用；没有旧部署也不能提前开放未完成适配的客户入口。

新库无历史部署时，旧 binary 清退清单和历史回填按限定范围登记“不适用”；从早期 schema 到目标 schema 的迁移与双身份 fixture 测试仍要保留。

### 3.2 实施边界与下一入口

Phase 1 已交付 [0013 扩展迁移](../../migrations/0013_membership_identity_policy.sql)、[成员生命周期 API](phase-01-api.md)和[写路径清单](phase-01-membership-path-audit.md)。管理事务按稳定顺序锁账号和成员，在等待后及提交前重验具体 actor session、实时权限、组织链及到期指纹；写请求必填非空、最多 500 字符且无控制字符的真实 `reason`，审计失败整体回滚。旧批量维护、联系人管理员和 seed 明确只写员工，不覆盖客户、不自动启用已停用员工。

旧登录、context、refresh、用户 OAuth 及应用凭据资格增加最小 **ENABLED EMPLOYEE** 守卫，阻止客户从旧入口取得员工凭据。此守卫没有完成具体成员／版本绑定；应用和客户端的允许集合／策略版本当前已建 schema 与约束，完整管理 API 和策略撤销消费仍留在 Phase 2。

Phase 1 完成时的下一实施入口为 **Phase 2：平台 context 与既有凭据绑定身份版本**。后续已按阶段完成至 Phase 6，当前指针见[台账](task-ledger.md)；真实生产创建仍默认关闭，SSO／OIDC 和两个 BFF 继续独立验收。UUID 专项的实际进展由其台账独立维护，身份文档不复制动态专项指针，也不接管其库或切流。

## 4. Q2／Q3／Q4：组织规则、客户闭环与 OIDC 配置

### 4.1 组织归属与客户最小接口

客户创建／绑定只接受管理员有权管理的真实组织和精确账号 ID，检查租户、组织有效性及当前管理范围。绑定既有账号须经过获授权的邀请或账号归属确认，并记录绑定来源；知道账号 ID 本身不构成绑定授权。一个账号在三个组织作为客户时建立三条 CUSTOMER 成员；在其中一个组织另为员工时再建立独立 EMPLOYEE 成员。客户挂根组织也不获得子树数据权限。

Phase 6 当前客户最小资源合同见[客户本人资料](phase-06-customer-profile.md)，阶段整体验收仍待完成：

| 接口 | 首版行为 |
| --- | --- |
| `GET /api/customer/context` | 返回当前账号、当前 CUSTOMER 成员、租户与组织；不返回员工角色、菜单和数据授权。 |
| `GET /api/customer/profile` | 只读当前账号的最少本人资料；服务端从已验证 context 取主体，不接受任意 userId 代读。 |
| `GET /api/customer/applications` | 成功时只返回精确登记且满足来源 client、应用、租户、组织和当前成员准入的单个应用；未登记或登记目标失效时拒绝访问。 |

兼容 DTO 如必须保留角色、权限、菜单字段，对客户固定返回空集合。客户 context 不消费同账号的员工行或 is_super_admin；员工 context 则继续按自身员工授权工作。

新增订单／工单等业务时再确定 tenant_id、organization_id、customer_membership_id、employee_actor_membership_id、允许动作与历史访问规则；不把员工经办数据当作客户本人数据。

### 4.2 开发域名、客户端与精确回调

以下是本地隔离开发候选，需在实施时配置 hosts、受信任开发证书和 HTTPS 网关；本轮未修改 hosts、证书或网关。

| 用途 | Origin／配置建议 | 身份限制 |
| --- | --- | --- |
| SSO issuer | `https://auth.saas.test` | 仅账号认证；不附带平台角色。 |
| Discovery | `https://auth.saas.test/.well-known/openid-configuration` | 元数据 issuer 精确等于上述 issuer。 |
| 员工控制台 | `https://console.saas.test`；注册配置别名 `platform-console-dev` | confidential USER client，仅 EMPLOYEE。 |
| 客户门户 | `https://customer.saas.test`；注册配置别名 `customer-portal-dev` | confidential USER client，仅 CUSTOMER。 |
| 控制台 callback | `https://console.saas.test/auth/callback` | 完整 URI 精确匹配，不使用通配符。 |
| 门户 callback | `https://customer.saas.test/auth/callback` | 完整 URI 精确匹配，不与控制台共享。 |
| 注销后返回 | 分别为 `https://console.saas.test/signed-out`、`https://customer.saas.test/signed-out` | 分客户端精确登记 post-logout URI。 |

client 别名不是已经签发的 client ID；注册后使用服务端实际生成的 ID 和独立 secret 配置 BFF。现有 OAuth playground 使用 `/callback`，新增 BFF 使用主方案的 `/auth/callback`，网关须优先路由至 BFF。

生产建议使用自有主域的 `auth`、`console`、`customer` 三个子域，实际域名在生产接入前冻结。开发与生产分别使用自己的 issuer、密钥、client 和精确回调；从同进程拆到独立服务时，只改变同一环境网关上游，保持该环境 issuer。

每个主机分别使用独立 `__Host-` Cookie 名称，设置 Secure、HttpOnly、Path=/，不设 Domain，初版采用 SameSite=Lax 与顶层 GET 授权回调。写请求校验 CSRF 和精确 Origin；state、nonce、PKCE verifier 保存在 BFF 的一次性服务端事务中。浏览器不长期保存 OIDC token；宿主需要的短期 context Bearer 走主方案的 `POST /auth/context-token`，refresh 留在服务端。

## 5. Q5／Q6：兼容范围、容量与故障预算

### 5.1 新库的协议兼容范围

- 不接纳历史 session、refresh、OAuth token、授权码或 device 流程状态；新凭据从新环境重新签发。
- 新建人员客户端默认只开放 Authorization Code＋S256；refresh 仅按 BFF 需要显式开启。password、device 不作为新客户端默认 grant，USER client 不允许 client_credentials。
- MACHINE client 仅允许登记的机器 grant，不能凭空成员集合扩大人员准入；不为新客户端引入 LEGACY_MIXED。
- 继续验证现有活动 SDK、MicroProps／Context／Notification 合同和门店／工单服务的应用鉴权。保留历史发行字节；活动 SDK 与消费者按本空库基线中的实际版本、v7 生成／输入与合同证据验收，可以复用专项已交付的代码和产物，不等待或冒领预览专项 U05 状态。
- 先建立源码消费者、用途、owner、grant、环境清单。演练代码只能证明代码中存在消费者，不能证明生产有使用；新库没有历史客户端也不能推断其他部署没有。
- 现有兼容入口按部署开关和明确用途登记，不能在 SSO 故障时自动恢复本地密码旁路。确需退役时，以消费者迁移、最长凭据寿命和无使用观测为依据，不编造日历停用期限。

### 5.2 初始测试目标

下列值是首轮隔离压测假设，需记录环境、CPU／内存、数据库、Argon2 参数和实测分位数。未测量前不得记为达标。

| 项目 | 建议测试目标 |
| --- | --- |
| 并发与持续负载 | 100 个并发会话；登录／换码／刷新合计 10 RPS，权威鉴权 100 RPS，持续 30 分钟。 |
| 突发 | 上述速率 2 倍，持续 5 分钟；观察队列、连接池和限流，不以无限并发实现吞吐。 |
| 权威状态校验 | p95≤100ms，p99≤300ms。 |
| 换码／刷新 | p95≤500ms，p99≤1s；密码认证单独统计，p95 候选≤1s。 |
| 超时 | 与现有门店／工单鉴权保持总预算 3s、连接上限 1s；新 SSO 换码／刷新初始候选总预算 3s。 |
| 撤销与隔离正确性 | 变更事务提交后，后续请求中的失效凭据与越权请求必须全部被拒绝；并发边界另做可重复的竞态测试。 |
| 故障行为 | 权威状态无法确认时返回 503 且不执行业务；安全敏感换码／刷新不自动重试，不使用成功授权缓存绕过撤销。 |
| 生产可用性候选 | 滚动 30 天 99.9%；明确排除预期用户错误与拒绝，依赖故障导致的 503 计入不可用。真实承诺在部署前结合实测确定。 |

指标分别记录登录、回调、授权、撤销和依赖故障，区分业务成功、安全拒绝、限流与依赖不可用。现有通用网关 65 秒超时不能替代认证服务的预算。

## 6. Q7：备份、密钥与恢复

| 层级 | 建议目标与实施条件 |
| --- | --- |
| 内部试运行 | RPO≤24h、RTO≤4h；每 12h 协调加密备份并远端回读认证；建议保留 14 天与 8 个周备份，每月做一次隔离恢复。调度和目标仍需实际建立与测量。 |
| 正式生产候选 | RPO≤15min、RTO≤60min；须增加持续 WAL／基础备份／timeline 管理／PITR，验证共库或跨库实际拓扑的一致恢复点，以及库外材料和密钥恢复。 |

当前恢复工具只证明协调 dump／隔离恢复合同，具有 24h 备份年龄门槛，文档明确尚未建立持续 WAL 和 PITR；不能据此认定已满足任何生产 RPO／RTO。

恢复集合应涵盖账号、成员、账号／身份／策略版本、客户端配置、认证签名私钥与历史公钥、部署配置和必要库外材料。签名私钥、备份密文和备份解密密钥分别托管，密钥不进入源码。新密钥激活前完成可恢复性验证；轮换保留旧公钥至对应凭据有效期和允许时钟偏差结束，泄漏事件走独立的立即撤销流程。

恢复后在开放流量前推进不会随备份倒退的失效边界，验证所有旧会话及派生凭据拒绝、新登录与两个入口可用。实际启用外部任务时，还要冻结／对账其库外效果，防止旧任务重放。

建议由运维 owner 负责备份、恢复执行和密钥托管，认证 owner 验证签名与会话，平台 owner 验证成员与授权，发布负责人负责切流。具体人员与值班方式在 Phase 12 前登记，本文不虚构已分配负责人。

## 7. Q8／Q9：工程落位与通知

### 7.1 工程位置候选

| 阶段 | 建议位置 | 边界 |
| --- | --- | --- |
| Phase 7～10 | 现有 `saas-plateform/backend/src/identity/` 或符合现有职责划分的模块 | 先建立消费者定义的认证 port 与单一写入 owner，不提前建大 workspace。 |
| Phase 11 | 同级独立仓库 `saas-customer-portal/`，内含 backend／frontend | Rust/Axum BFF＋React/Vite，独立 Cookie、缓存和登录客户端。 |
| Phase 12 | 同级独立仓库 `saas-identity/` | 薄入口、厚库；仅通过网络协议服务平台，不跨仓依赖平台业务 crate。 |

以上候选目录均相对于本工作区根目录；两个新仓库当前不存在。同 PostgreSQL 实例／数据库过渡可接受，先明确表的 owner、独立运行角色和单一迁移作业，不为目录整齐强制迁移已有表的 schema。

现有开发前端／API 为 3000／3001。独立身份 API 3041、门户前端／BFF 3040／3042 可作为未来候选端口，实施时再核对占用；公开入口仍通过各自 HTTPS origin，不将内部端口作为稳定 issuer。

### 7.2 通知边界先完成，客户业务后开放

首版客户门户不显示通知入口，服务端也不接受未登记客户用途的发送。现有 APP／SYSTEM／缺省组织广播仅选择有效 EMPLOYEE。

Phase 4 仍须实现组织通知绑定具体 `recipient_membership_id`、`recipient_member_type`、`recipient_identity_version`；发布去重、收件去重、列表、单条、未读数、批量操作、socket-context 和逐条投递采用同一身份边界。成员停用、移除和身份版本改变时，对应连接与缓存失效，同组织另一身份保持独立。

身份版本变化后的旧代通知保留审计，不自动回到新代收件箱；停用后重启也不自动恢复旧代消息。本新库没有历史通知回填任务。后续需要客户通知时，再登记真实事件、门户路由允许清单及跨代归档访问规则，不能直接开放员工 `/micro/*` 深链。
