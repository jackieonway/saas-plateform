# Project browser gate

Use the root Node 24.18.0/npm 11.16.0 toolchain. Browser tooling is isolated from production frontends in this package: exact Playwright 1.64.1 and Socket.IO 4.8.4 provide browser control and an isolated notification transport fixture. The standalone eleven-suite `run.mjs` uses HTTP fixtures and does not connect to a database. The managed CI browser gate additionally runs a separate real Axum/PostgreSQL grant UI harness after those suites.

```powershell
npm ci --prefix tests/browser
node tests/browser/install.mjs chromium
node tests/browser/run.mjs --browser chromium --report target/browser-chromium.json
```

Install all four frontend packages with their locks first (`frontend`, `mini-services/micro-vue`, `mini-services/micro-jquery`, `examples/websocket`). The mandatory manifest runs every existing host browser script plus the independent chat example, with scenario selectors removed from child environments. A missing browser, nonzero script exit, zero checks, or required skip fails the gate. Reports distinguish assertion pass counts from failed suite counts and include the actual product/browser/Node/Playwright-lock versions. An output report must be new; previous evidence cannot be overwritten accidentally.

Linux CI installs browser system dependencies in the dedicated runner image:

```sh
node tests/browser/install.mjs --with-deps chromium chrome msedge
node tests/browser/run.mjs --browser chromium --report /tmp/owned-output/chromium.json
node tests/browser/run.mjs --browser chrome --report /tmp/owned-output/chrome.json
node tests/browser/run.mjs --browser msedge --report /tmp/owned-output/msedge.json
```

Chromium, real Chrome and Microsoft Edge are required in the PR and candidate browser matrix; the product channels never fall back to bundled Chromium. On Windows the runner uses existing Chrome/Edge installations without replacing or installing product browsers. Missing required products fail their gates. Actual versions must be recorded; running one installed version does not prove the latest two stable releases are supported.

Downloaded browser binaries default to this package's ignored `.browsers/` directory. The fixed Linux CI image layer `/opt/ci/browser/.browsers` is the only additional accepted `PLAYWRIGHT_BROWSERS_PATH`. The source package still installs its own locked JavaScript dependencies. Personal Playwright caches, Codex caches, `PLAYWRIGHT_MODULE` and arbitrary executable overrides are not used.

Firefox and WebKit are explicit extension checks only: install the requested engine with the same installer and invoke `--browser firefox` or `--browser webkit`. They do not replace Chromium/Chrome/Edge and are never silently skipped. A WebKit run is an engine check, not Safari product acceptance.

The managed `scripts/ci/linux-runner.mjs --gate browser` allocates an owned private PostgreSQL container and invokes the complete 14-step CI gate. Its additional `data-grant-ui-live` step selects exactly one ignored Rust harness (`data_grant_ui_tests::browser_management_closes_grant_loop`) and requires sixteen named actual UI checks, the observed product/version, four audit request IDs matching PostgreSQL and successful cleanup of both platform and independent business databases. The existing work-orders backend performs real introspection/context and SQL queries with the same ordinary app token: SELF one record, ORG two, outside records absent, then revoke 403. A sanitized management preview PNG and its SHA-256 are kept in the controlled report path. Fixture-only children do not receive database settings. `tests/browser/run.mjs` and the optional Firefox/WebKit workflow remain the eleven-suite fixture entry and cannot establish this live closure or the future Rust business migration. See [Phase 15](../../docs/validation/phase-15.md) for actual scope and results.

The fixture browser tests exercise actual Vite/React UI and micro application assets. Their intercepted APIs and Socket.IO test server validate UI behavior only. They do not establish business authorization, PostgreSQL behavior, deployment HTTPS, or future Rust/Socket.IO compatibility; those are separate gates.

The mandatory manifest declares 209 check groups per product across eleven suites. The nine earlier suites remain mandatory with their previous total of 183, including micro-host 47 and route-permissions 64. The micro-host suite retains the 29 earlier groups covering registered SDK consumers and compatibility plus permanently pending trusted load, mount, update and unmount. These regressions use the production ten-second deadline and a valid long-lived authorization fixture: they verify cancellation, the sticky trusted fault, independent iframe mounting, rejection before another trusted script executes, late settlement, organization switching and actual host-document reload recovery. A real browser also re-evaluates the runtime from fresh module URLs in the same Window, checking that both the active queue and subsequent fault survive module replacement and that faults remain recognizable across module instances. This exercises the execution-domain risk behind dev HMR; it does not claim to test every Vite HMR transport path. The suite retains the existing normal serial lifecycle and final unmount checks.

Phase 8 adds 18 mandatory groups to that same micro-host suite: two entry/profile/context consistency races, five bounded recovery cases, four permanent authorization/protocol refusals, one recovery case preserving a poisoned trusted domain, two lifecycle-without-update compatibility cases for trusted and actual iframe applications, and four real work-orders UI cases. The work-orders addon is imported and counted by the main suite, using its real Vue application, the registered SDK and isolated HTTP fixtures. It verifies that theme updates preserve a pending submission and list state, route changes affect relevant reads, renewed credentials reject old replies and removed grants revoke operations. Scenario selectors are removed by the mandatory runner, so these groups run on every required product. Prior-phase results cannot establish that the changed Phase 8 source passed.

Phase 9 adds the independent `phase9-navigation` suite (`tests/phase9-navigation-browser.mjs`) with 14 mandatory groups. It exercises lazy and shared application-menu requests, command-palette queries, rapid selection and A→B→A races across the rail/dashboard, invalidation after direct navigation, an unrelated menu failure, root-only and personal pages, unknown authorization refusal, separate create and detail-read permissions, and a cross-organization response whose transport ignores cancellation. The tests use the real host UI with isolated API fixtures. The local entry is `npm --prefix frontend run test:auth:navigation:browser`; the full mandatory runner also executes the eight retained suites and requires all groups on every required product.

Phase 10 adds `phase10-session` (`tests/phase10-session-browser.mjs`) with 17 mandatory groups using two real pages in the same browser context. The local entry is `npm --prefix frontend run test:auth:session:browser`. The suite checks concurrent refresh, replacement login, logout, organization changes, closed pages and unknown outcomes, together with missing-capability behavior. The full mandatory runner retains all nine earlier suites. Browser evidence must bind actual Web Locks/storage capabilities, the observed product and version, and the frozen source inputs. Chrome and Edge's two latest stable major versions require separate runs of this session suite in fixed official-product images; the ordinary three-product gate alone does not establish that version matrix. Any diagnostic scenario filter must be absent from mandatory execution. Test declarations and successful browser installation do not count as runtime acceptance.

Phase 29 adds `phase29-host` with nine mandatory production-build checks per product. `node tests/phase29-browser-gate.mjs` always rebuilds its own ignored `target/phase-29/gate-<product>/dist` before running the real React application with isolated API fixtures: public module exclusion, on-demand palette and shortcut, render throw/local retry, chunk404/manual reload, pending Outlet shell persistence, denied management route, HTML creation/release handoff, editing immutable entry metadata and unregistered ESM validation. The manifest now totals eleven suites / 209 checks. Performance is a separate controlled Chromium experiment (`phase29-build.mjs before|after`, `phase29-performance.mjs before|after`), not a timing assertion inside the concurrent browser matrix. Do not overwrite the original baseline evidence. See [Phase29](../../docs/validation/phase-29.md).
